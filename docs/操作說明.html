Loop Engineering 完整操作說明

一套用量感知（token-aware）的自主編碼任務排程器 ＋ 協作器。它把編碼任務排入佇列、以必填欄位審核把關，並在你的 Claude 用量低於日/夜門檻時，逐一派給無頭的 Claude Code 在隔離的 git worktree 中執行，跑完你的驗證步驟後停進「待結案」欄，等你收尾。設計為 24/7 常駐 Linux 主機、透過 Tailscale 遠端監看／暫停。

MAX 訂閱 · 以用量百分比排程 單一 Node 程序 ＋ SQLite 看板 · SSE 即時更新 M1–M4 完成

01這是什麼

Loop Engineering 解決一個問題：你想讓 Claude Code 自動、連續地完成一批編碼任務，但又不能燒爆你的訂閱用量。它是一個常駐的「調度大腦」，核心行為是：

  • 排入佇列：把每個編碼任務（目標、計畫、驗證步驟、repo）建成一張卡片。
  • 把關（gate）：必填欄位不齊，任務無法進入排程。
  • 用量感知調度：每 60 秒一個 tick，只有在 session／weekly 用量百分比低於當前時段門檻、且有足夠 runway 時，才派工。
  • 隔離執行：在專屬 git worktree 中跑 Claude Code（無頭、串流 JSON），自動 commit，再跑你的驗證指令。
  • 停進待結案：驗證通過 → review 欄等你人工收尾；失敗 → failed。
ℹ️為什麼用「百分比」而非「金額」？本工具是為固定的 MAX 方案設計，排程依據是用量百分比（session 5 小時窗、weekly 窗），而非美金花費——訂閱制下額度才是限制。

架構一句話

單一 Node 程序 ＋ SQLite（WAL 模式）。沒有 Redis／訊息佇列——用行程內的 60 秒 tick 搭配 mutex 與 max_concurrency。用量透過 TokenBar 的 oauth/usage 契約讀取（session／weekly %），並有 ledger 後備。

02任務生命週期

每張任務卡片會沿著這條狀態機前進：

draft→（審核）→ queued→ running→ verifying→ review→ closed
running 遇到問題 ⤵ blocked（斷路器／硬暫停，額度內 → 自動 resume） attention（timeout／執行錯誤／續跑用盡 → 保留現場，等你決定） failed（使用者中止／放棄 → 終態）
🔀verify 通過後自動收尾（第 13 章）：拉最新 base 併入分支 → 重跑 verify → push 分支 → 自動併回 main 並 push GitHub；遇衝突自動生一個「merge 任務」。所以到 review 時通常已經在 main 上了，你按結案只是最後放行（並放行鏈上的下一個任務）。
狀態意義看板欄位
draft剛建立，尚未通過入場審核Draft · 入場審核
ready審核通過、尚未加入排程Ready
queued已入列，等待調度派工Queued
runningClaude Code 正在 worktree 中執行Running
verifying正在跑你的驗證步驟Verifying
blocked被斷路器或硬暫停中斷，額度內保留 session 自動續跑Queued（可自動 resume）
attention待確認：執行出問題（timeout／執行錯誤／setup 失敗／續跑用盡／最終 verify 失敗），已保留 worktree／session／HANDOFF，卡片顯示失敗原因＋log，等你決定續跑／重來／放棄Review · 結案
review驗證通過（通常已自動併回 main），待你人工結案Review · 結案
failed你中止或放棄的終態Review · 結案
closed你已結案，流程結束（並放行鏈上下一個任務）Closed

04遠端存取（MacBook Air / 手機）

看板只走你的私人 Tailscale 網路（tailnet），不對公網開放。由於已啟用 token，第一次開啟必須帶 token，之後瀏覽器會記住。

步驟 1 — 取得帶 token 的完整網址

在主機終端機執行（基於安全，token 不寫在本手冊內；此指令會印出可直接開的完整網址）：

echo "https://addis-b850m-ds3h.tailffdb68.ts.net/?token=$(grep '^LOOP_API_TOKEN=' ~/.config/loop-engineering/env | cut -d= -f2)"
📖這份說明線上就看得到：https://<主機>/docs/操作說明.html，對話頁標題列的「？」裡也有連結。

步驟 2 — MacBook Air（已在 tailnet，免安裝）

  • 把上一步印出的網址貼進 Safari / Chrome → 看板出現。
  • token 會存進 localStorage，之後直接開 https://addis-b850m-ds3h.tailffdb68.ts.net/ 即可（免 token）。可加入 Dock。

步驟 3 — 手機

  1. 安裝 Tailscale App（App Store / Play 商店）。
  2. 登入同一帳號 addislyu@，打開開關。
  3. 瀏覽器開同一串帶 token 的網址 → 可「加入主畫面」變 App 圖示。
⚠️只能用 HTTPS + MagicDNS 主機名這個網址。憑證綁定 addis-b850m-ds3h.tailffdb68.ts.net；http://100.65.248.121:4711 這類 IP 網址不通（服務只綁 127.0.0.1、對外一律經 tailscale serve）。
🔓想免 token？私人 tailnet 本身就是邊界。要拿掉第二層驗證：
sed -i 's/^LOOP_API_TOKEN=/#LOOP_API_TOKEN=/' ~/.config/loop-engineering/env
systemctl --user restart loop-engineering
之後所有裝置直接開網址即可。代價：tailnet 內任何裝置皆可存取、無驗證。

狀態可用動作

工作流程（/flow.html）

修問題請改用問題單（第 5b 章）。工作流程留給評比（AI 實作節點選 2 個以上模型）、拆成多個任務與其他進階用途，之後會移除。

PRD 精靈與新工作合併成一頁。一個工作流程就是一份 PRD：畫布上的節點依任務真正的生命週期排列——需求 → 準備環境 → AI 實作 → 驗證 → 驗收門檻 → 人工核可 → 合併 → 結案。驗收門檻有三個出口：通過往下走、無法判定（缺能力、沒量到）轉人工核可、未通過沿虛線退回 AI 實作自動續跑（次數是全域 max_resumes，用完轉到總覽的「需要你處理」）。

  • 開始（/flow.html#new）：一兩句話寫要做什麼、選 repo 與分支、選流程類型（程式任務／評比（多模型）／拆成多個任務），可以再點一個驗證方案（驗證指令、驗收指標、保護路徑、產出物、人工清單、前置指令、領域一次帶好）或變更類型，或貼上 PRD 轉成流程。按「產生流程」就開一份草稿。
  • 編輯器（?draft=）：點節點開三欄——輸入（這一步拿到什麼）｜參數／設定（要填的東西）｜輸出（這一步會產生什麼）。缺必填的節點會亮 ⚠，上方「N 個問題」一按就列出並可跳過去；閘門的隱性必填（範圍、非範圍、驗收標準、目標至少 15 字）都攤開在需求與門檻節點。AI 實作節點選 2 個以上模型就變成評比（最後接「最終量測 → 評審」）。要人工核可就在驗收門檻節點的「人工核可」加一條要人確認的事，畫布上會多出人工核可節點（核可時才合併）。「拆成多個任務」的流程是 需求 → AI 拆解 → 子任務 → 結案，驗證指令填在「子任務」節點，AI 拆解時照著給每一步配上驗證。「文件」分頁是送出的 PRD 原文，也可以直接改 Markdown。草稿自動儲存。
  • 檢查／開始執行：「檢查」跑一次入場閘門（含本地模型複核）並把問題對到節點；「開始執行」送出並排入，「存成任務」只建任務先不排入（之後在它的執行紀錄或總覽按「加入排程」）。從驗證方案開始的會把方案記在任務上（驗收頁因此能選圖資）；選「拆成多個任務」會建一個 epic，由 AI 拆成依序執行的子任務。
  • 執行紀錄（?task=，總覽、評比都能點進來）：同一張圖依任務實際走到哪裡亮燈，退回的虛線會標「未通過 N 次 → 自動續跑 n/2」；下方紀錄面板列出每一次嘗試的準備環境、AI 實作（時間、token、自己在沙盒試跑幾次、有沒有用 ncu）、每個驗證步驟（花多久、最後幾行輸出）與驗收門檻（每條指標、各遮罩的長條圖）。點畫布上的節點會選到最近一次嘗試的那一步。拆成多個任務的流程在這裡列出它的子任務（點一個就打開那一步自己的工作流程）。手機上畫布一開就放大在正在跑（或卡住）的那一步，紀錄改成上下排。

評比（/benchmarks.html）

  • 每一場：卡片列出每場評比；進行中的在最上方顯示「題目 → 實作 n/N → 最終量測 → 評審」。
  • 單場儀表板：勝出與進度 → 每個模型一張成績卡（主要指標的大數字、對門檻與基準的子彈圖、「比基準快 N×」、每次嘗試的結果點、評分／時間／token）→ 各遮罩（各項）量測分組長條圖（門檻虛線、基準灰色、可切對數）→ 迭代路徑（每次嘗試的起訖、等本地 GPU 的空檔、自己試跑與 ncu）→ 每次嘗試的量測折線（過關區塗綠）→ 評審分數四準則點圖 → 品質 vs 花費時間散點 → 評審意見與完整表格。
  • 基準：有驗收指標的評比在評分時會把參賽前的原始程式（參賽組記下的 base commit）用同一套驗證量一次（benchmarks.baseline_json）；已經評完的評比按「量基準」補量（POST /api/benchmarks/:id/baseline，評比進行中不行，量測要獨占 GPU）。
  • 戰績：依領域、本地／雲端、最少場次篩選；每個領域一張推薦卡（本地模型還做不來／可以交給本地／做得到但不如雲端／僅供參考）、模型 × 領域通過率熱圖、第幾次才過的堆疊條、通過率對平均時間散點、兩兩對戰矩陣（GET /api/benchmarks/h2h），完整表格收在最下面。
  • 新評比：比什麼（看板任務／工作流程草稿／驗證方案或自己出題／內建題庫）→ 誰來比 → 誰來評，其餘收在進階。

API用途

驗證步驟現在會記錄各自花的時間（task_runs.verify_json 的 ms）；看板的即時串流改成每秒只組一份快照給所有連線、入場審核結果依任務快取、log 只讀檔尾 64 KB，開很多分頁也不會拖慢引擎。

05b問題單：從問題到 PR

修 bug、加功能、調效能、改演算法，都從問題單開始。你只要給三樣東西：repo 網址（或 Gitea issue 連結）、一段描述，有的話再加截圖。其餘由 Loop 偵測並提出分析，你確認之後它才動手：在隔離的 worktree 修、到設好的機台跑檢查、開 Gitea PR、回 issue 留言。驗收是每個 repo 設定一次的檢查，像 CI 一樣一項一項亮綠燈或紅燈。每個 LLM 步驟都可以只用本地模型（見下面的「公司模式」）。

ℹ️問題單就是一張草稿任務。它是 draft 狀態的任務：總覽、需要你處理、晨報都看得到，按「開始修」之後走同一套生命週期（第 2 章）。分析卡存在任務上；需求文件（PRD）仍是任務的計畫，由 Loop 照範本組好，介面上不再有表單要填。工作流程與驗證方案（第 5a、26d 章）還在，留給評比與進階用途，之後會移除。

四步流程

步驟在哪裡做什麼
1 開單左側欄「問題單」（/fix.html），或對話頁貼 Gitea 的 repo 或 issue 網址，寫發生什麼事、在哪裡、期望應該怎樣，Ctrl+V 貼截圖，按「請 Loop 分析」。第一次用到的 repo 會先跳出匯入對話框（約 1 分鐘，見下面「Repo 設定」）。
2 看分析卡同一頁（/fix.html?id=t_…）30 秒到 2 分鐘後出現：可能原因與位置、重現方式、驗收清單、機台、模型、預估。哪一塊不對，就按那一塊的「改一下」。
3 開始修分析卡的「開始修」（主管模式是「送出核可」）Loop 在隔離的 worktree 修，自己先跑到綠；引擎再到機台跑全部檢查。修不好就換下一個本地模型再試。通過後做本地自評、開 Gitea PR、在 issue 留言。
4 看結果結果頁（/task.html?id=…）結論色塊、Loop 的自評、檢查清單（每項都能看紀錄）、圖資逐案例、程式碼 diff、嘗試記錄。按「合併」（走 Gitea PR 合併，可以順便關 issue），或按「退回修改…」寫一句話讓 Loop 接著改。

問題單頁（/fix.html）的細節：

  • 描述框：寫「發生什麼事、在哪裡、期望應該怎樣」，可以直接貼錯誤訊息、螢幕截圖、Gitea 的 issue 或 repo 連結。標題可以留空，Loop 會取。描述至少 10 個字、而且選好 repo，「請 Loop 分析」才會亮；「先存草稿」先存起來，之後再回來分析。
  • 貼網址會自動偵測：issue 連結 → 出現「issue #12 · 標題」晶片，描述帶入 issue 內容、repo 鎖定、issue 的附件圖變成截圖；repo 連結 → 帶入 repo。還沒匯入的 repo 會出現「匯入 aoi/cf-aoi」內嵌卡。
  • 截圖：貼上或拖進來，最多 6 張、每張 4 MB 以內，瀏覽器先縮到 1600 px。截圖上的文字由本地模型或 OCR 讀出來，用在找原因與實作模型的提示（見「準確度設定」的 intake_vision）；圖檔本身也附給實作模型。
  • 右欄屬性：Repo（已匯入的清單，最後一項「＋ 匯入 Repo…」）、分支、類型（錯誤修復／功能／效能／演算法，分析後自動填，可改）、機台（唯讀摘要，帶健康點）、模型（「由 Loop 依領域挑」，可改）、優先（低／中／高）、來源（issue 或對話）。
  • 分析中：表單下方是進度清單，每 3 秒更新：讀取 repo 地圖 → 讀截圖（有截圖時）→ 比對錯誤字串與符號 → 提出重現方式 → 挑選必過檢查 → 本地模型複核。分析沒完成時可以「重試」，或「改成手動填寫」（分析卡以空白的編輯狀態打開，自己填重現方式、勾檢查）。
  • 對話頁也能開單：描述問題並貼上 repo 或 issue 連結，Loop 會開一張問題單，在對話裡顯示精簡的分析卡，回覆「確認」就開始修。輸入框旁的「轉成問題單」晶片把目前的文字與截圖直接開成問題單；回答底下的「轉成任務」變成「開問題單／留待辦」。

分析卡標頭上的狀態：

分析中→ 就緒→（主管模式）→ 待核可→ 已排入→ 執行中→ 已完成

對應的任務狀態：就緒＝分析好的 draft；已排入＝queued；執行中＝running／verifying；已完成＝review／closed；attention／failed 顯示「需要處理」。

分析卡：每一塊在說什麼

標頭一行：標題 · 類型 · aoi/cf-aoi @ main · 狀態。下面五塊，每塊右上角有「改一下」的鉛筆，只把那一塊切成編輯。

區塊內容可以怎麼改
可能原因與位置最多 6 列：檔案 · 一句話 · 證據行（「第 214 行：…」）· 最近修改（「2 週前 · fix(control): …」）。Loop 從描述與截圖文字抽出錯誤字串、識別字、路徑、中文介面字，在 repo 裡搜尋計分，排出最可疑的檔案，附上每個檔案最近的 commit。找不到時寫「沒有找到明確位置；Loop 會從描述裡的關鍵字搜尋。」刪掉一列；加一個檔案（路徑從 repo 地圖自動完成）。
重現方式二選一。「有現成的重現指令」：指令＋徽章「修改前必須失敗」＋分析時試跑的結果（「現在：✗ 失敗（exit 1）— 正確」，或警告「現在就通過了，可能重現不了」）。「請 Loop 先寫一個會失敗的測試」：寫出會在哪個測試檔新增，驗收時確認它修改前紅、修改後綠。切換兩種方式、改指令。
驗收清單這次會跑的檢查，長得像 GitHub 的 checks：☑ 必過 · 建置 · cmake --build build（aoi-1）、☑ 必過 · 單元測試、☑ 重現 · 修前紅、修後綠、☐ 圖資回歸 · dataset-2026Q2 · 正確率不低於 98.7%、時間不超過 5.3 s。必過的不能取消勾選；選用的可以勾掉。「管理這個 repo 的檢查」連到 Repo 頁。
執行條件機台（含上次檢查時間）· 模型與理由（例：「qwen3-coder-next（本地；C++ 領域通過率 71%）」）· 預估（規模、約幾分鐘、要不要等夜間時段 local_task_window）· 修不好時（最多自己修幾次、之後換哪個本地模型，來自 fix_attempts／fix_escalation）。改模型。
Loop 還不確定本地模型複核時覺得沒講清楚的地方；沒有就不顯示。主管退回的原因也放在這裡。每條按「回答」：答案接在描述後面，分析重跑。這些問題不會擋住「開始修」（除非設了 prd_require_llm）。

頁尾：開始修（主管模式：送出核可）、取消（刪掉這張草稿和它的截圖）、看需求文件（唯讀抽屜：Loop 照範本組出來的 PRD，也就是實作模型實際讀到的計畫）。

🔗按下「開始修」之後。它照樣要過入場審核（第 6 章），沒過會列出原因。這張單要跑的檢查（連同基準換算出來的門檻）存在任務上：之後再改 repo 的檢查，已經排入的任務不受影響。

驗收清單與「檢查」

檢查是每個 repo 設定一次的驗收項目（Repo 頁的「檢查」分頁），之後每張問題單都會跑。你只回答兩件事：怎麼跑、怎麼算過。LOOP_METRICS、{dataset}、sandbox:、容器路徑、指標名稱都由 Loop 產生或偵測。

類型怎麼跑怎麼算過
建置／測試／自訂一行指令（Windows 機台用 PowerShell 語法）。exit 0，或指標門檻。
重現腳本指令＋「修改前必須失敗」（預設勾）＋測試檔 glob（例 tests/**）。修改前失敗、修改後通過（紅→綠）。
圖資回歸選一個圖資＋指令範本，例 run_inference --in {images} --out {out}：{images} 圖片資料夾、{answers} 答案檔、{out} 輸出資料夾（Loop 會收回來比對）。正確率不低於基準／時間不超過基準 ×1.1／自訂門檻。
人工一行清單文字。在結果頁由人勾選。

編輯器（對話框）的類型分段有五種：建置 · 測試 · 重現腳本 · 圖資回歸 · 自訂，欄位隨類型改變。其他欄位：在哪裡跑（引擎主機或某台機台，帶作業系統與健康點）、怎麼算過（exit 0／指標門檻／不比基準差）、逾時（分鐘，預設 20，check_timeout_min）、產出物、保護路徑（提示：量尺、評估程式、答案檔）、必過。

檢查清單每一列：名稱 · 類型 · 在哪跑 · 怎麼算過 · 最近一次（✓ 2 小時前／✗／未跑過）· 必過 · ⋯（試跑一次／編輯／停用／刪除），可以拖曳排序（建置排在測試前面）。還沒有檢查時會寫「還沒有檢查。先加一個建置或測試檢查；之後每張問題單都會跑它們。」，旁邊的「用偵測到的指令建立」一次建好建置與測試兩項。

  • 試跑一次＝偵測指標：編輯器頁尾的「試跑一次」在 repo 的預設分支跑一次，輸出即時顯示，結束時列出「偵測到的指標」晶片。指標門檻的名稱只能從這些晶片選，還沒試跑過會先請你試跑，不必再猜名字。圖資回歸的指標名稱固定：correct_rate、mismatches、missing、total、time_ms。CLI 做同樣的事：loop check list <repo id>、loop check trial <檢查 id>、loop check baseline <檢查 id> <run id>（第 7 章）。
  • 基準：圖資回歸試跑完會顯示「基準：正確率 98.7%，5.1 s（@ 3f2a1c）」，按「設為基準」記下那個 commit 與數值。「不比基準差」在建立任務時換算成具體門檻（正確率 ≥ 基準、time_ms ≤ 基準 ×1.1），所以之後改基準不會影響已排入的任務。checks_baseline_refresh（預設關）打開後，夜間會自動重量預設分支已經往前走的基準。
  • 重現紅→綠：驗收時，引擎把測試檔（這次新增的，加上符合 glob 的）放到 base 的暫存 worktree 跑，必須失敗；再在修改後的版本跑，必須通過。結果寫成「修改前：✗ exit 1 · 修改後：✓ exit 0」。在機台上跑的重現檢查，兩次都在那台跑。這是給本地模型最硬的護欄：它不能靠改測試過關。
  • 圖資回歸：圖資是一個 Gitea repo，放原圖資料夾與答案檔，在 Repo 頁的「圖資」分頁連結。執行時：機台上 clone 或更新圖資 repo（有 LFS 就 git lfs pull，機台要裝 git-lfs）→ 代入 {images} {answers} {out} 執行 → 把 {out} 拉回 Spark → 引擎比對：答案檔的 json、csv、labels（每張圖一個 YOLO .txt）三種格式自動判斷，標籤相同才算對，兩邊都有框時 IoU 要 ≥ 0.5 → 產生指標與逐案例結果。軟體輸出在 {out}/overlays/ 的覆蓋圖會一起收回。比對在引擎主機做，機台不需要 Python。
  • 檢查的名稱就是步驟名稱：失敗原因、需要你處理、PR 內文、晨報都寫「單元測試」，不會出現 check:ck_…。實作模型在 LOOP_TASK.md 看到每項檢查的名稱、指令與在哪台跑，並被要求把本地能跑的（建置、測試、重現）自己先跑到綠。
  • 舊的驗證方案會轉成對應 repo 的檢查；驗證方案頁保留到移除為止。
⚠️AOI 軟體目前只有 GUI：圖資回歸要先有命令列入口。圖資回歸需要一個「給一個資料夾、輸出結果檔」的 headless 命令列入口。還沒有的 repo，編輯器會寫「這個 repo 還沒有命令列入口，圖資回歸無法自動跑」，旁邊的「請 Loop 幫這個 repo 加命令列入口」會開一張範本問題單。在那之前，圖資項目以人工驗收的形式進驗收清單，結果頁附圖讓人勾選。建議每個 AOI repo 的第一張問題單就是這一張：加一個命令列入口。

機台

機台是一台能用 SSH 登入、裝了 git 的電腦（Linux 或 Windows），repo 的檢查在上面跑，不需要 Docker。它和第 26b／26c 章的 GPU 沙盒主機（exec_hosts）是兩回事：沙盒主機照舊，在機台頁最下面摺疊的「GPU 沙盒主機（進階）」唯讀列出。

機台頁（/machines.html）是一張表：名稱 · SSH · 作業系統 · 標籤 · 狀態（● 正常 10 分鐘前／● 連不上／○ 未檢查）· 用它的 repo · ⋯。還沒有時寫「還沒有機台。加一台能 SSH 進去、裝了 git 的電腦。」

新增／編輯的欄位說明
名稱小寫英數、_、-，最多 40 字，不能叫 local 或 engine。之後不能改名（檢查用名稱指到它）。
SSH 目標、埠user@host，或 ~/.ssh/config 裡的別名。只用金鑰登入，引擎不會問密碼。
作業系統Linux／Windows。不確定就留「自動」，第一次檢查時會記住。
Shell檢查指令用哪種語法：自動（Linux＝bash、Windows＝PowerShell）／bash／PowerShell／cmd。
工作目錄repo 複本與圖資放這裡：Linux 例 /srv/loop、Windows 例 C:\loop。只能用英數、_、.、-，不能有空白。
標籤、說明標籤例 cuda、aoi-v3、camera；說明是給模型看的：這台有什麼。
取碼方式自動（由檢查決定）／Gitea／由 Spark 傳檔，見下面。

SSH 金鑰怎麼放（在 Spark 上，用跑引擎的那個帳號）：

  1. 還沒有金鑰就建一把：ssh-keygen -t ed25519；公鑰在 ~/.ssh/id_ed25519.pub。
  2. Linux 機台：ssh-copy-id user@host（不是 22 埠就加 -p 埠），再手動 ssh user@host 一次，接受 host key。
  3. Windows 機台（內建的 OpenSSH Server）：一般帳號把公鑰加進 C:\Users\<帳號>\.ssh\authorized_keys。帳號屬於 Administrators 群組時，Windows 只讀 C:\ProgramData\ssh\administrators_authorized_keys，而且這個檔只能讓 Administrators 和 SYSTEM 存取： 
    icacls C:\ProgramData\ssh\administrators_authorized_keys /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"
    一樣從 Spark 手動 ssh 一次，接受 host key。

健康檢查：機台頁的「檢查」，或 loop machine check aoi-1。每一行是 ✓ 正常、✗ 要處理，或 ⚠ 知道就好。結果存在機台上（機台頁的狀態欄）；作業系統、Shell、取碼方式還是「自動」的，會記住這次偵測到的值。

行在看什麼沒過時怎麼辦
SSH 登入能不能用金鑰登入，以及是什麼系統，例「aoi@aoi-1（Windows 11，PowerShell 5.1）」。機台設定寫的作業系統和實際不同，也會在這一行標出來。「無法以金鑰登入…」：照上面放公鑰；「host key 還沒接受」：在 Spark 上手動 ssh 一次。
git版本。Linux：sudo apt install git。Windows：裝 Git for Windows（安裝時勾選加入 PATH），並登入 Gitea 一次讓 Credential Manager 記住。
Gitea機台自己讀不讀得到 repo（在機台上跑 git ls-remote）。讀得到：「能讀 http://gitea.corp:3000（已存認證）」，取碼方式用 Gitea；讀不到：改用由 Spark 傳檔（較慢）。還沒有 repo 用這台時略過。要讓機台自己抓：Linux 執行 git config --global credential.helper store，再手動 git ls-remote <網址> 一次，輸入帳號與 token；Windows 手動 git ls-remote <網址> 一次，讓 Git Credential Manager 記住登入。
工作目錄可不可寫、還剩多少空間，例「C:\loop 可寫，剩 212 GB」。Linux：sudo mkdir -p /srv/loop && sudo chown <帳號> /srv/loop；Windows：建立 C:\loop，並給登入帳號寫入權限。
Python版本。⚠ 找不到也沒關係：圖資比對在引擎主機做。
GPUnvidia-smi 看到的 GPU。⚠ 沒有的話，只有需要 GPU 的檢查會受影響。
repo 複本每個用這台的 repo 在機台上的 commit 與時間，例「cf-aoi @ 3f2a1c（2 小時前）」。還沒有：第一次跑檢查時會 clone。
圖資快取圖資 repo 有沒有抓到這台。還沒抓：第一次跑檢查時會抓。

取碼方式：Gitea 還是由 Spark 傳檔

  • Gitea（機台讀得到 Gitea 時）：引擎先把任務分支推上 Gitea，機台在自己的複本 <工作目錄>/repos/<repo> 抓那個分支、強制切到要驗的 commit。建置產物留著，下次可以增量編譯。機台用它自己存的認證讀 Gitea，引擎不會把 GITEA_TOKEN 傳過去。
  • 由 Spark 傳檔（讀不到時）：引擎把 worktree 複製過去——Linux 用 rsync（被 .gitignore 的檔案不傳也不刪，建置產物留著），Windows 先清掉舊的複本再用 scp 整份傳。機台不必連 Gitea，但比較慢。
  • 機台上的複本是 Loop 自己的，隨時會被強制切換；任何人的 checkout 都不會被動到。
怎麼執行LinuxWindows
指令bash -lc，外面包 GNU timeout。PowerShell（-EncodedCommand，輸出 UTF-8），用 Start-Process＋WaitForExit 計時；Shell 選 cmd 時改用 cmd /c。sshd 登入後預設給 cmd 還是 PowerShell 都沒關係。
逾時exit 124（10 秒後還沒停就強制結束）。連同子行程一起結束，exit 124。
輸出stdout＋stderr 合併，保留最後 20,000 字。
連不上exit 255，顯示「連不上 aoi-1」。
指令長度20,000 字。4,000 字（長的請寫成腳本檔再執行）。

一台機台同一時間只跑一件事：兩張任務或一次試跑不會搶同一份複本。

loop machine add aoi-1 --ssh aoi@aoi-1 --os windows --work-root 'C:\loop' --labels aoi-v3,camera --desc "AOI 產線同型機"
loop machine check aoi-1      # 逐行 ✅／❌／⚠️；有 ❌ 時 exit code 1
loop machine list             # 每台的設定與上次檢查結果

Gitea issue 串接

準備（只要一次）：

  1. loop config set gitea_url http://gitea.corp:3000（一台 Gitea）。
  2. 在 Gitea 建一個 token，寫進 systemd 的環境檔 ~/.config/loop-engineering/env：GITEA_TOKEN=…，再 systemctl --user restart loop-engineering。token 要能讀寫 repository、在 issue 留言、改標籤、關閉 issue、開 PR 與合併 PR。
  3. token 只放在環境變數：clone、fetch、push 經 GIT_ASKPASS（scripts/git-askpass-env.sh）交給 git，不出現在指令列、不寫進 .git/config，也不會傳給機台。不要把它放進設定或網址。
  4. 要讓 issue 留言裡的連結點得開，設好 LOOP_PUBLIC_URL（第 8 章）。

接單：

  • 貼 issue 連結：在問題單頁或對話裡貼 …/aoi/cf-aoi/issues/12。issue 的標題與內文帶進描述，附件圖變成截圖，任務的來源記成 gitea:aoi/cf-aoi#12。repo 要先匯入。
  • 標籤自動接單：在 Repo 設定打開「從 Gitea issue 自動接單」並填標籤（例 loop）。引擎每 gitea_poll_interval_min 分鐘（預設 10）掃一次開著、帶這個標籤的 issue；每個 issue 只會開一張問題單，並留言「Loop 已接單，正在分析」。是引擎去問 Gitea，不需要讓 Gitea 連回 Loop（不用開 webhook）；沒有任何 repo 設標籤時，輪詢完全不跑。
  • 接進來的問題單照常分析，要有人按「開始修」才會開始（主管模式要主管核可）。

回報的每一種留言（只有從 issue 來的問題單會留言；同一種不會重複發）：

時機留言內容

準確度設定

全部預設關，舊任務完全不受影響。在設定對話框的「修問題的準確度（問題單）」（左側欄齒輪），或用 loop config set 修改，最多 60 秒生效。找原因與位置、repo 地圖、過去修法，分析時一律會用；下面的旗標決定要不要另外交給實作模型，以及要不要多加護欄。

旗標預設做什麼
failing_firstfalse先失敗再修：分析時試跑重現指令，必須失敗；派工前引擎在乾淨的 worktree 再跑一次，要是通過了就停在需要處理「重現指令在修改前就通過了」，不花任何算力。失敗的輸出放進 LOOP_TASK.md 的「重現輸出（修改前）」。
fix_attempts（空）自己修幾次：空＝驗證沒過時和中斷續跑共用 max_resumes（和以前一樣）；填數字＝驗證沒過時另外計這麼多次修正，中斷續跑照舊用 max_resumes。
fix_escalation（空）修不好換模型：local:<id>，逗號分隔（id 見 loop local list）。fix_attempts 用完就依序換下一個本地模型，在同一個分支冷啟動；LOOP_RESUME_CONTEXT.md 帶著每一次失敗的紀錄，並交代「前一個模型試過…，請換一個做法」。清單用完才停在需要處理。要先設 fix_attempts 才會自動換；結果頁的「再試一次（換模型）」不受這個限制。
local_self_reviewfalse本地自評：驗證通過後，本地模型看 diff 與檢查結果，寫出「改了什麼／為什麼／風險／範圍外的改動」，放在結果頁與 PR 內文，也記進過去修法。失敗不擋任何事。
repo_map_injectfalse把 repo 地圖（語言比例、目錄、進入點、建置與測試指令、最多 3,000 個符號）放進 LOOP_TASK.md 的「Repo 地圖」，截到 repo_map_budget_chars（8000）字。
fix_ledger_injectfalse把這個 repo 過去類似的修法（最多 5 筆）放進 LOOP_TASK.md。
domain_routingfalse依領域挑模型：依評比與快篩的戰績，挑這個領域最好的本地模型（分析卡寫出理由）。任務自己指定的模型仍然優先。
intake_visionauto截圖怎麼讀：auto＝載入的模型能看圖就讓它讀，不能就用 intake_ocr_cmd，都沒有就標「截圖未辨識」；model／ocr 只用其中一種；off 不讀。模型能不能看圖，Loop 從模型權重的設定自動判斷。
intake_ocr_cmd（空）OCR 指令，{file} 是截圖路徑，例 tesseract {file} - -l eng+chi_tra。要先在 Spark 上安裝 tesseract 與繁體中文語言包。

建議組合：

  • 剛開始：全部維持預設。分析卡照樣有原因與位置、重現方式、驗收清單。
  • repo 有可靠的重現指令或測試：開 failing_first。重現指令在修改前就通過，代表重現不了，這時停下來最省。
  • 交給本地模型修：開 local_self_review（結果頁與 PR 有自評可看）和 repo_map_inject；過去修法累積幾筆之後，再開 fix_ledger_inject。
  • 一個模型修不好就換：fix_attempts 填一個小數字，fix_escalation 列一兩個本地模型。每換一次模型都要重新載入 vLLM（100 GB 級模型約 6 分鐘，第 26 章），建議配合 local_task_window 在夜間跑。
  • domain_routing：等評比或快篩在你的領域累積足夠場次再開；少於 3 場的推薦只能當參考（第 26 章）。

公司模式：只用本地模型

一個開關：cloud_llm_allowed=false（設定對話框「機密」→「公司模式：所有步驟只用本地模型」，或 loop config set cloud_llm_allowed false）。關掉之後，公司的程式碼與描述不會送到任何雲端模型。預設 true，和以前一樣。

步驟公司模式下
分析、截圖辨識、本地自評本來就只用本地模型。
實作（任務的模型）任務、default_model 或 route_* 指到雲端模型（sonnet、opus…）時，派工改用目前載入的本地模型（沒有載入就用第一個啟用的），事件記一筆「公司模式：模型 … 改用本地模型 …」。模型設定也不能再改成雲端模型。依領域挑模型時，「做得到但不如雲端」的本地模型也會被選。
規劃器（拆成多個任務）改用本地模型（planner_backend 視同 local）。
LLM 評審（驗證模式 llm）改用本地模型（llm_judge_backend 視同 local）；判不出來照舊轉人工。
知識蒸餾改用本地模型（knowledge_distill_backend）；設成 off 就不蒸餾。
評比評審bench_judge_model 可以設成 local:<id>，由載入的本地模型評（比雲端評審弱）。
任務結束時的缺口審查（gap review）不跑，由本地自評補上。
請雲端複核，以及其他一定要用雲端模型的功能拒絕並說明：「公司模式：只用本地模型（cloud_llm_allowed=false），這個功能需要雲端模型」。

不開公司模式，也可以個別把 planner_backend、llm_judge_backend 設成 local，把 knowledge_distill_backend 設成 local 或 off。

  • 待核可卡片：出現在總覽與對話頁右欄「需要你處理」原有的待核可群組：「待核可（開工）」· 標題 · 「○○ 想請 Loop 修這個；看分析卡再核可」。每個人都有「看分析卡」；只有主管有「核可」，其他人看到的是「等主管核可」。送出時另外推播一則（ntfy）。
  • 退回：主管可以寫原因退回，單子留在草稿，原因顯示在分析卡的「Loop 還不確定」。
  • 主管是誰：manager_users，逗號分隔的 ts:<登入>、name:<名字>、local。建議只放 ts:（Tailscale 驗證過的）；name: 開頭的名字任何人都能自己填。

結果頁

就是原本的驗收頁（/task.html?id=…，第 26d 章），改成 PR 頁的樣子。標頭：標題 · 狀態 · cf-aoi @ main · 「PR #34」「issue #12」連結 · 第 N 次嘗試 · 模型。分頁：結果 · 程式碼 · 試跑 · 需求（唯讀的分析卡＋需求文件）。「結果」分頁由上而下：

  1. 結論色塊：綠「4 項檢查都過，重現測試從紅變綠」／紅「沒過：單元測試（aoi-1）」／藍「正在跑檢查 2/4：單元測試」。
  2. Loop 的自評：改了什麼、為什麼、風險、範圍外的改動（local_self_review 關著時，這裡寫沒有自評）。
  3. 檢查清單：✓ 建置 · aoi-1 · 41 s · 看紀錄、✓ 重現 · 修前 ✗ → 修後 ✓、✓ 圖資回歸 · 正確率 98.7% → 99.0% · 5.1 s → 4.9 s · 看每張、✗ 單元測試 · exit 1 · 看紀錄。「看紀錄」開抽屜，看輸出的最後一段。
  4. 圖資回歸檢視器（有跑圖資回歸時）：總數、正確（修前→修後）、變好、變差、沒輸出；「只看變化」；表格 案例 · 輸入圖 · 期望 · 修前 · 修後 · 結果，點一列左右對照（輸入圖、軟體有輸出時的覆蓋圖、差異）。
  5. 嘗試記錄：每次嘗試一行，例 第 1 次 · qwen3-coder-next · 沒過 單元測試 · 12 分 … 第 3 次 · glm53-flash · 通過。

固定在下方的動作列：

  • 合併：匯入的 Gitea repo 走 Gitea PR 合併；對話框裡可以勾「在 Gitea 留言並關閉 issue #12」（只有從 issue 來的單才有）。
  • 退回修改…：寫一句話（「寫下要改什麼，Loop 會在同一個分支接著改」），任務回到佇列；從 issue 來的單會在 issue 留言。
  • 交給同事…：把這張單交給另一個人，並留一則紀錄。
  • 再試一次（換模型）：紅燈時出現。換成 fix_escalation 的下一個本地模型（或你挑的），在同一個分支冷啟動重新排入；前一個模型的提交留著，失敗紀錄寫進 LOOP_RESUME_CONTEXT.md。清單裡沒有下一個時會說「沒有下一個模型可以換」。

試跑、人工驗收清單、下載 zip／發佈到 Gitea，照第 26d 章。

06新增任務與入場審核

修 bug、加功能、調效能、改演算法，請開問題單（/fix.html，見第 5b 章）：給 repo 或 issue 網址、描述與截圖，Loop 提出分析，驗收由 repo 設好的檢查負責；按「開始修」時一樣要過下面的入場審核。工作流程（/flow.html#new，見第 5a 章）與驗證方案還在，留給評比與進階用途，之後會移除。要直接填任務欄位（產出檔案、部署這類工具），用總覽標題列 ⋯ →「新增單一任務（進階）」。入場審核（gate）會逐項檢查；未通過的任務無法加入排程，卡片上會標紅缺項。

欄位必填說明 / 審核規則
Title是任務標題。
Goal是目標描述，不可空白。
Plan是計畫參照：存在的 .md/.html 檔路徑，或合法 URL。
Tool是claude-code／mock（零 token 測試用）／generic（無 git、產出檔案的非編碼任務）／plan（Epic 自主規劃——見下方「任務類型與驗證模式」與第 13 章）／deploy（部署任務，不派工給 agent——見第 19 章）。

Repo path是*存在的 git repo 目錄。mock／generic 略過
Base branch是*存在的基底分支。mock／generic 略過
Complexity—S/M/L（預設 M）；決定逾時與預估用量。

任務類型與驗證模式

Tool 決定任務在哪裡、怎麼跑；Verify mode 決定怎麼判定完成。兩者互相獨立，可自由組合（例：generic ＋ llm 用來跑一份分析報告，由 LLM 對照 rubric 判斷是否合格）。

Tool執行位置Git 收尾用途
claude-code專屬 git worktree（loop/<id> 分支，從 base 切出）完整（見第 13 章）：commit → push → 併回 base → PR一般編碼任務。
mock暫存目錄（每次 run 全新建立，用完即棄）無（零 token 測試/演練用，不代表真實產出）排程器/斷路器/watchdog 的零 token 測試。
generic持久化產出目錄 ~/.local/share/loop-engineering/outputs/<id>（跨 resume 保留，結案也不會被清掉）完全略過——不建 worktree、不 commit、不 push、不併回、不開 PR非編碼工作：報告、資料分析、一次性腳本、設計產出等。真的呼叫 Claude Code（非 mock），只是不碰 git。
plan（Epic）不執行任何工作區——AI 規劃器把目標拆成子任務，子任務才各自建 worktree無（本身不改任何程式碼；子任務照常走完整收尾）一句話丟一個大目標，自動拆成 2–6 個子任務並依序自主執行——見第 13 章「Epic 自主規劃」。
deploy不派工給 agent——直接在 repo_path 執行 deploy_cmd（環境 auto_deploy=1），或產出 outputs/deploy-<id>/DEPLOY.md 部署包（auto_deploy=0）無（不是編碼任務，沒有 diff 可併）把 environment 從知識標籤升級成真正的部署目標——見第 19 章「環境與部署」。
📄generic 的產出怎麼看？看板卡片顯示「📄 產出 N」徽章；點開卡片可看產出目錄路徑與檔案清單（名稱＋大小，最多列 ~50 個）；也可呼叫 GET /api/tasks/:id/result 或 MCP 的 loop_task_result 取得同樣資訊。
Verify mode怎麼判定完成備註
command（預設）執行 Verify steps，全部 exit 0 才算過。至少要有一條指令；generic 的指令在產出目錄執行。
llm把變更（claude-code／mock 是 git diff；generic 是產出目錄的檔案清單＋小型文字檔摘錄）連同 Rubric 交給 LLM 判官，回覆 pass/fail。需填「驗收標準 Rubric」；判官不可用（無 claude CLI／用量已達硬上限）時絕不自動放行，改判為 manual。
manual一律停在待人工驗證，由你依 Rubric／產出親自確認後按合併或結案。可免填 Verify steps；claude-code 會請 agent 寫一份 VERIFY.md 交接手動驗證清單。

Verify mode 可複選（逗號分隔，如 command,llm）：只要其中一種判定失敗，就整體算失敗；只要包含 manual，最終一定停在待人工驗證。

09三層預算保護

為避免燒爆用量，派工到執行有三道獨立防線：

① 派工前 gate

tick 時先看用量快照：若 session/weekly 已達當前時段門檻，或 runway 不足 min_runway_min，就不派工。

② 執行中斷路器

執行期間若用量衝破 hard_limit_pct（95%），立即中斷該 run（SIGINT → SIGKILL），任務轉 blocked（保留 session，用量降回後自動 resume）。

③ 每run watchdog

每個 run 有依複雜度而定的逾時（S/M/L = 15/45/120 分）；逾時即殺並標 failed。

🛡️另有內層保險：PreToolUse 的 budget-guard.mjs hook 會在硬上限阻止工具使用——即使排程層失守，被派出的 Claude 也會被擋下。

13自動化：Git 收尾與任務鏈

這一章講三件讓 Loop Engineering 能自己一路做下去的機制，以及人與引擎的分工。

1 · running 的標準流程（Git 自動收尾）

每個 claude-code 任務跑完後，引擎自動走這條收尾（全部可用第 8 章的旗標關閉）：

  1. 派工時從 fetch 過的最新 origin/<base> 切 loop/<id> 分支（不再從過期本地 main）。
  2. Claude Code 修改 → 自動 commit → 跑你的 verify 步驟。
  3. 把最新 base 併進分支；若有變動重跑一次 verify。
  4. push 分支備份 → FF-only 自動併回 main 並 push 到 GitHub。
  5. 卡片進 review，徽章顯示 ✓ 已合併。
🛡️安全保證：所有網路 git 操作都有 30 秒逾時、失敗不會卡住引擎；併回一律 fast-forward-only，絕不改動你的髒工作區、絕不強推。無法乾淨 FF（例如你的 base 有未推的本地 commit）就降級為 待合併，卡片上按合併再試。按合併時，引擎會先把最新的 base 併進任務分支；分支因此有變動就重新跑一次驗證，通過才併回，沒通過就不合併、任務留在 review，並跳出原因。
🧩遇衝突自動解：併回若衝突，引擎自動建一個 merge 任務（標題 [merge] …），交給 Claude Code 拉最新 base、解衝突、跑 verify，再自己走一次收尾。你不用手動處理。

2 · attention（待確認）：出問題時保留現場交回人工

過去出問題只有「自動續跑」或「直接 failed」兩種。現在多了一個待確認狀態：watchdog 逾時、執行錯誤、setup 失敗、續跑用盡、最終 verify 失敗，都會落到 attention（顯示在 Review 欄），保留 worktree／session／HANDOFF，卡片列出失敗原因與 log。你有三個動作：

動作作用
續跑沿用原 session 與 HANDOFF，從中斷處接續（給一次額度）。
重來清掉 worktree 與 loop/<id> 分支、歸零續跑計數，從最新 base 重新開始。
放棄標記 failed 終態（可選一併清 worktree）。
🧷使用者「中止」是終態：按中止（或 abort）的任務直接 failed、不會偷偷自動復跑。想暫停但保留可續跑，用硬暫停（pause --hard）→ 轉 blocked。

3 · 任務鏈（depends_on）：嚴格 A → B → C

要讓任務一個做完才做下一個（例如彼此會改到同一批檔、或後者依賴前者的成果），用依賴鏈，避免多個任務同時從舊 base 切分支互相衝突：

# CLI：B 依賴 A
npm run loop -- add --title "B" --goal "…" --plan ./B.md \
  --repo /path --base main --verify "npm test" --depends-on <A的id>
  • 帶 depends_on 的任務會被押住不派工，卡片顯示 ⏳ 等 t_xxx。
  • 前置任務結案的那一刻，引擎自動放行下一棒（dep_auto_queue）。
  • 前置若 failed 或被刪除，後者押住等你處理，絕不誤跑。
  • MCP 也支援：建 B 時說「依賴 A」。

4 · Epic 自主規劃（coding_tool=plan）

ADO＋Copilot 仍需要人把 Epic 拆成 Feature／Story 才能派工；Loop 的差異化能力是：只丟一個大目標，AI 規劃器自動拆成一條 depends_on 子任務鏈並自主執行到底——就是你原本手動拆任務鏈的動作，改由 Loop 自己做。

  1. 建一個 tool=plan 任務（Title/Goal 照填；Plan 欄位當作「Epic 說明書」，可以寫得比一般任務詳細）。Repo／Base／Model／Environment 這幾欄若填了，會被子任務繼承；不填也可以（純規劃）。
  2. 派工時不會建立 worktree，而是呼叫規劃模型（default_model，通常比知識蒸餾用的 haiku 更強），把「目標＋Plan＋相關知識」丟給它，要求輸出 2–6 個子任務（含各自的 goal／verify steps／複雜度，彼此若有先後用 order 表示）的嚴格 JSON。
  3. 規劃結果materialize 成一串真正的 claude-code 子任務：parent_id 指回這個 Epic、依 order 用 depends_on 串成鏈、繼承 Epic 的 repo/base/environment/model。第一個子任務（若通過 gate）直接 queued，其餘留 draft，交給既有的任務鏈機制（見上方第 3 節）依序放行。
  4. Epic 本身立刻結案（closed，卡片顯示「已拆解為 N 個子任務」）——它的工作就是產生子任務鏈，之後全程由子任務照常跑收尾／verify／人工核可。
  5. 規劃失敗（模型沒回應、輸出解析不出來、用量已達硬上限）Epic 轉 attention，可續跑重試或改手動拆任務。
🧬看板怎麼看：Epic 卡片顯示「子任務 n/m 完成」rollup 徽章；子任務卡片顯示「↳ epic: t_xxx」回指徽章；點開任一張卡片的詳情視窗都能看到完整的子任務清單與各自狀態。
⚠️Epic 任務不需要（也不會用到）Verify steps／Repo／Base——這些檢查全部略過；真正需要驗證的是它產生出來的子任務。
📐SDD 規格模式（sdd_specs，預設關）：預設每個子任務都共用同一份 Epic 說明書當 plan_ref。開啟 sdd_specs 後，規劃器改為每個子任務生成一份自足規格 spec-*.md（背景／驗收情境／限制／out-of-scope）當各自的 plan_ref——讓沒有其他背景的實作者（或便宜模型）只讀那份規格就能可靠完成。這正是把「便宜模型」下放到實作階段（model_routing，見第 8 章）的前提。關閉＝規劃器提示與子任務 plan_ref 與改版前完全一樣（零影響）。

  • 任務執行中可以自己查（task_mcp_enabled，預設開）：派工時會產生一份只含唯讀伺服器的 MCP 設定（loop／loop-fs，不含 gh 或任何會寫入的工具）給 Claude Code，並在 LOOP_TASK.md 多一段「查知識庫」明寫什麼時候該查：要改設定檔／機台參數／網路硬體前先 loop_recall，需要背景脈絡用 loop_search。設定檔寫在資料目錄、不在 worktree 裡，所以永遠不會被 git add -A 掃進任務分支；工具名稱一併進 --allowed-tools，查詢不會停在權限詢問。
  • 看得到有沒有進去：看板點開任務 →「知識注入」區塊列出會注入幾條、用掉多少預算、每條的相關度，以及最常見的失敗——知識在某個 repo: scope 裡、但這張任務不指向那裡，會直接寫出「有 N 條在 X，這張任務拿不到」。CLI 是 loop knowledge preview <taskId>；要把一批知識換 scope 用 loop knowledge rescope --from repo:/path --to global [--kind constraint] --yes（不加 --yes 是試跑）。
  • 任務可指定環境：新增任務的 Model 旁有 environment 欄（如 company／home）→ 該環境的知識隨之注入。
  • CLAUDE.md 匯出：loop knowledge export --repo <路徑> 把環境約束寫進該 repo 的 CLAUDE.md（標記區塊、冪等）——公司電腦上的 Claude/Cursor 也共享同一份知識。
🧠已預載你的環境：公司（Win11＋Python 3.8.10、3.8 語法約束）、家用開發機（Linux＋RTX 2080 CUDA）、數位轉型辦公自動化專案、在家開發帶去公司部署的流程偏好。之後建任務時 environment 填 company，產出的程式碼就會自動遵守 3.8 相容。

知識圖譜視覺化（Obsidian 式 [[wikilink]] ＋ 多跳 ＋ force-directed）

在節點 body（或 ~/SSoT vault 裡的 markdown 檔）寫 [[標題]] 就會自動建關聯：節點對節點的 wikilink 直接變成一條 links-to 關聯（跟手動建的關聯一起顯示、可刪，但只要 body 裡還留著該 [[wikilink]]，下次存檔就會自動重建）；vault 裡的 markdown 檔本身會成為圖上的文件節點（方形，跟節點的圓形區分），連到它連結的節點或其他文件——這一段解析在每次 loop ingest run 之後全庫重跑一次，所以連結目標晚於連結本身被 ingest／新增也會在下一次自動接上。

  • 開啟方式：知識星圖一打開就是整張圖；某節點列的「關聯」鈕則以該節點為中心開一張多跳鄰居圖（右上角「展開跳數」可調 1–6 跳）。
  • 操作：拖曳空白處平移、滾輪縮放、拖曳節點喬位置、點一下節點（不拖曳）會即時向伺服器多要一跳鄰居併入目前的圖（既有節點位置不會被打斷）。
  • 篩選：面板內有 kind 篩選、來源篩選（節點的 source／文件所屬的 ingest 來源）、標籤與 scope 關鍵字過濾，以及「顯示文件節點」開關（關掉只看策展知識，不看語料文件）。
  • 純 vanilla 實作：整張圖是手刻 canvas 2D force-directed（web/graph-layout.js 純運算＋web/brain.js 畫面／互動），沒有外部圖表庫、沒有 CDN，符合看板一貫的 textContent-only（canvas 文字是像素，本來就不是 HTML，不會有注入風險）。

知識圖譜關聯（auto-relate）：自動推斷節點間的關係

手動建關聯很容易越積越少——這功能用混合策略幫知識庫補關聯，同樣草稿制、永不自動核准：先用既有的向量索引（vec_nodes，sqlite-vec，cosine 距離）取每個節點嵌入空間裡最近的 5 個鄰居當候選配對（避免 N² 全配對），再用一次 haiku 呼叫幫候選配對判斷關係型別（runs-on／constrains／deployed-at／uses／part-of／related）並濾掉沒有實質關聯的配對——輸出的邊一律以草稿關聯入庫，跟既有邊（同來源、去向、關係型別）重複的一律略過，不會產生重複邊。

  • 怎麼觸發：知識星圖標題列的「推斷關聯」；或 CLI loop knowledge relate [--limit N]（--limit 控制單次最多評估幾組候選配對，離越近的配對優先，預設 20）；或 API POST /api/knowledge/relate。
  • 怎麼審核：知識庫頁「草稿關聯」區塊列出所有待審核的建議邊（來源／關係／去向＋理由），逐條「核可」或「退回」——核可後才會出現在圖譜與任務注入裡；退回不會刪除紀錄，只是不再視為待審。
  • 絕不自動生效：草稿關聯在核可前不會出現在「🕸 圖譜」畫面，也不會被派工時的知識注入（knowledgeContext）當成一跳關聯使用——跟草稿節點的審核邏輯完全對稱。
  • 零 token 前提：沒裝 claude CLI，或本節 session 用量已達 hard_limit_pct，都不會呼叫 LLM（也不會消耗嵌入運算）；沒有觸發前，圖譜與任務注入行為完全不變。

15SSoT／RAG／擷取管線

第 14 章的知識庫是策展層——小量、人工核可、會注入任務 prompt。這一章是它的擴充：一個語料層（documents／chunks），把整個 codebase、筆記 vault 甚至 GitHub issues 都受治理地擷取進同一個 loop.sqlite，支援混合語意檢索（RAG）與可追溯的引用——但只在被查詢時才選擇性拉出，絕不整段塞進任務 prompt（維持第 14 章「零影響」的策展層不變）。

🗂️兩個資料平面。策展圖譜層（knowledge_nodes/edges，第 14 章）＝小量、人工核可、注入 prompt；語料層（documents/chunks，這一章）＝大量原始擷取內容，只供 RAG 檢索、選擇性拉 top-K。兩層以 doc_links／node_chunk_links 連結（例如 vault 筆記的 [[wikilink]]、或蒸餾草稿的語料佐證）。

來源登錄與擷取管線

先登錄一個來源（sources 表），再觸發擷取：

# 登錄：git repo（受 .gitignore、只取已追蹤檔）／folder／Obsidian 風格 vault
loop ingest add --git ~/Coding/LoopEngineering
loop ingest add --vault ~/SSoT
loop ingest list
loop ingest rm <source_id>

# 擷取：全部已啟用來源，或指定一個
loop ingest run
loop ingest run <source_id>
  • 受治理 walker：git 來源用 git ls-files（尊重 .gitignore）；folder/vault 用遞迴 walk。一律排除 node_modules/dist/.git、二進位、鎖檔；.env*／.pem／id_rsa 等金鑰檔名整檔跳過；檔案大小超過 ingest_max_file_kb 也跳過。就算檔案通過了這層，內文裡看起來像私鑰區塊／AWS／OpenAI／GitHub／Slack token／key="..." 這類樣式，也會被逐一遮蔽成 [REDACTED] 才進索引。
  • chunker：markdown 依標題切塊、程式碼依函式/行窗切塊，每個片段都記 start_line/end_line 供之後的引用；每個片段被嵌入／建 FTS 索引的文字都會前綴該文件的 title，確保只存在標題裡的關鍵詞（例如專有名詞、work package 主旨）也能被向量與關鍵字檢索到。
  • 增量、bi-temporal：以檔案內容 sha256 比對——沒變的檔案整個略過（skipped_unchanged），變了的檔案舊版標記 invalid_at（保留歷史，不刪除）並產生新版文件／片段；來源裡消失的檔案同樣被標記失效，而不是砍掉重練。
  • 觸發方式：CLI loop ingest run [source]、MCP loop_ingest／loop_sources、REST POST /api/ingest／GET /api/sources。

OpenProject 來源

第五種來源類型：把 OpenProject 伺服器裡的 work packages（含主旨＋描述）與 projects 擷取進 SSoT，之後能用中文語義跟程式碼一起檢索。不重新實作 OpenProject client——重用使用者既有的 ~/Coding/OpenProject_Exec_Report/op_api.py（零外部相依、Python 3.8 相容，已封裝認證／分頁／自訂欄位／normalize）。

loop ingest add --openproject ~/Coding/OpenProject_Exec_Report
loop ingest run <source_id>
  • 運作方式：Node 端注入式 spawn scripts/openproject_dump.py（僅 stdlib）——把 --openproject 的 repo 路徑加進 sys.path 後 import op_api，呼叫其 get_work_packages／get_projects；每筆輸出一行 JSON，Node 端逐行解析後走既有的 chunk→embed→store 管線；壞掉的單一行只會被跳過，不會讓整次擷取失敗。
  • 增量規則跟檔案型來源不同：檔案型來源用內容 sha256；OpenProject 用該筆項目的 updatedAt（無此欄位才退回 sha256）——伺服器端已修改的 work package 才會被重新擷取，沒改的整批略過。
  • 登錄時做的事：loop ingest add --openproject <repo> 會讀該 repo 的 config.json（預設路徑，--op-config 可覆寫）取出 op_base_url 當作來源的 uri（供之後 loop_search 的 scope 過濾用）——只取這一個欄位，op_api_key 全程不讀取、不複製、不寫入 log，僅由 op_api.py 自己在 spawn 出的 python 行程裡本機讀取使用。
  • 只取兩種項目（wiki／工時暫不做）：--kinds work_packages,projects（預設兩者都取）；每份 work package 文件的可檢索文字＝主旨＋描述＋少數有意義分類欄位（類型／狀態／負責人／專案），活動留言的時間戳雜訊不收錄（title 仍另存 #<id> <主旨> 不變）；引用連結（document.uri）指到 <op_base_url>/work_packages/<id>；project 文件指到 <op_base_url>/projects/<identifier>。
  • 沒登錄 openproject 來源＝零行為變化；沒設定 ingest_openproject_python 時預設呼叫 python3（公司 Windows 部署若執行檔叫 python，改這個設定即可，不需要改程式碼）。

混合 RAG 檢索

語料層可用混合檢索查：FTS5 trigram 全文（跟第 14 章知識庫搜尋同一套中文友善索引）⊕ 向量 KNN 語意搜尋，兩路排名以 RRF（Reciprocal Rank Fusion）融合，回傳帶引用（來源路徑／行號／分數）的片段。

  • 本機 GPU 嵌入：rag_enabled=false（預設）時完全不會嵌入、不會載入模型——自動退回純 FTS 全文檢索，一樣可用，只是少了語意召回。開啟後用 embed_model（預設 BAAI/bge-m3，1024 維、多語含中文）透過 voice-venv 的常駐 worker 嵌入，同一顆 GPU 與語音 whisper worker 共用、互斥、閒置自動釋放 VRAM（embed_worker_idle_min）。
  • sqlite-vec：向量存在 vec_chunks／vec_nodes 兩個 vec0 虛擬表；loadExtension 失敗（例如平台沒有對應的 .so）會安靜降級為 FTS-only，不會讓伺服器起不來。
  • 怎麼查：MCP loop_search（回帶引用的片段，適合問「這段邏輯在哪裡」）、REST GET /api/rag/search?q=...。
  • 任務內自動帶語料（旗標，預設關）：rag_inject_task_context=true 時，派工除了第 14 章的策展知識，還會額外拉該 repo scope 的 top-K 語料片段，附進 LOOP_TASK.md 一個獨立的「相關語料 (RAG)」段（有 char 預算上限）；關閉＝完全不影響 prompt。

快速記錄（capture）：一句話寫進 SSoT vault

不想手動開 Obsidian 建檔時，用擷取：寫一則 markdown 筆記進已登錄的 SSoT vault，並立即索引，馬上就能被 loop_search 搜到。跟第 14 章「＋ 新增」的策展知識節點是完全分開的兩層——擷取寫進語料層（documents/chunks），不會注入任何任務 prompt；要留一條「以後每個任務都要遵守」的長期事實，還是用 loop_remember／知識庫頁的「＋ 新增」。

  • MCP：loop_capture（text 必填，title 留白則取內文第一句，tags 選填）。
  • 網頁：知識星圖（/brain.html）標題列的「擷取」開一個輕量對話框，寫完按「寫入」，成功後顯示新增了幾份文件／幾個片段。
  • REST：POST /api/capture（{"body":"...","title":"...","tags":[...]}）。
  • 寫入的目的地是第一個已啟用的 kind=vault 來源——先用 loop ingest add --vault ~/SSoT 登錄一個，擷取才有地方寫；沒登錄會回 400 錯誤說明原因。

週期性 re-ingest

不想每次改完 vault／repo 都手動 loop ingest run，可開啟排程器自動幫你重跑：

鍵預設說明
ingest_auto_pumpfalse開啟後，伺服器 tick loop 會依 ingest_pump_interval_min 週期自動對每個已啟用來源做一次增量 loop ingest run（背景執行、不擋 tick，失敗下次照樣重試）；沒改的檔案增量略過，成本很低。關閉＝完全不會自動觸發，維持手動／MCP／REST 觸發的舊行為。
ingest_pump_interval_min30兩次自動 re-ingest 之間至少間隔幾分鐘。伺服器（重）啟動後第一個 tick 會先跑一次，補上停機期間的變更。

蒸餾 ↔ 語料佐證（可追溯）

第 14 章的自動蒸餾在任務結案時萃取候選知識草稿；現在多一步：草稿產生的當下，會用它的標題對語料庫做一次混合檢索，把支持這個草稿的原始片段記下來（node_chunk_links，relation=evidences）。知識庫頁的草稿列多一顆「佐證」鈕，點開可看到這些片段的路徑／行號／摘錄——核可前先看它是不是真的有根據。查無片段（語料庫是空的、或標題找不到對應內容）就完全沒有佐證區塊，不影響原本的核可／退回流程。

17Backlog 用量預估

回答「還能不能再加任務？」：把既有的每任務估計（est_pct_* / est_weekly_pct_*）加總成一個 backlog 預測，純讀取、不影響排程或預算行為。「pending」= 非終態任務（draft/ready/queued/running/verifying/blocked，排除 closed/failed/review/attention）。

  • Weekly 是累加約束（整週不會中途歸零）：weekly_backlog_pct = 所有 pending 任務的 estimateWeeklyPct 加總；weekly_headroom = max(0, weekly_max − weekly_now − weekly_backlog_pct)。
  • Session 是逐窗口的（每 5 小時歸零一次）：不把 backlog 的 session 估計加總，只回報其中最大的單一任務估計（largest_task_session_pct）與是否塞得進一個 session 窗口（largest_task_session_fits，即 ≤ hard_limit_pct − safety_reserve_pct）。
  • verdict：依 weekly_headroom／capacity_more_M 分四級——plenty（餘裕多）／some（還加得下幾個）／tight（勉強擠得下）／full（額度已滿）。

四個入口都看得到同一份預估：總覽上方六格的用量格（游標停著，見第 5 章）、loop forecast CLI（見第 7 章）、GET /api/forecast（見附錄）、以及 MCP 的 loop_status（見第 12 章）——問「Loop 還能加幾個任務？」它就會回。

📐只讀既有估計，不新增任何調度判斷——關掉這個功能（不呼叫它）對排程/預算行為零影響。

18執行紀律（實驗性，預設關）

社群傳的「Superpowers 6.0 = 速度 2 倍／token −50%」是誤讀了 Superpowers 自己 6.0 對比 5.x 的 changelog（不是對比原生 Claude Code）；獨立測試顯示平均省 ~14%、簡單任務反而更貴，而且它的工作流程本來就偏吃 token。把整個 plugin 裝進 Loop 是淨負面：Loop 無頭派工的 --allowed-tools 沒有 Skill/Task，它的技能大多根本不會被觸發（描述注入的 token 白花）；brainstorming 技能會反問使用者，對無人值守是致命的；worktree／plan／code-review／subagent 相關技能還會跟 Loop 自己的 worktree.ts／planner／gapReviewer／verify 重複＋衝突。

所以：不安裝 plugin。唯一真正可搬、不衝突、便宜的部分，是三個「純提示詞」紀律：test-driven-development、systematic-debugging、verification-before-completion。這裡把它們濃縮成一段選配的 ## 執行紀律 提示（見 src/orchestrator/prompt.ts），完全不含 subagent、不含反問，由 prompt_discipline 開關控制（預設 false ＝ 對 LOOP_TASK.md 零影響）。

  • 怎麼開：看板 ⚙ 面板「執行紀律（實驗性）」，或 loop config set prompt_discipline true。
  • 怎麼量測：開/關各跑幾個可比較的任務，用 GET /api/metrics 看「執行紀律 A/B」資料——依每個結案任務最新一次 run 的 discipline 分組，列任務數、平均實際 session %／任務（session_pct_before/after 差值加總）、待確認率、平均續跑次數、平均週期。同一份資料也能從 GET /api/metrics 或 loop forecast CLI 尾端看到。
  • 誠實原則：這是量測工具，不是背書——效果好壞看你自己的任務跑出來的數字，不是相信這段文案。
💡Superpowers 這個 plugin 本身很適合互動式 Claude（brainstorming 等技能靠使用者來回才有價值），只是不適合 Loop 這種無頭排程執行——兩者的使用情境不同，不是互斥。

SDD × 便宜模型 A/B（同一套量測骨架）

核心假設：把規格寫到夠精準，便宜模型（haiku）就能達到強模型面對模糊目標的水準，且更省額度、rework 更少。「更好」＝同一個 5h/週額度窗口出更多貨、變異更小。這是要用資料驗證的假設，不是可直接假定成立——所以先量測再開分流。

  • 怎麼標記：新增任務時用 loop add --experiment <名>（或 MCP loop_add_task 的 experiment 參數）。這是純標籤，完全不影響排程／入場審核。
  • 怎麼比：挑幾個代表性目標，各建兩次——A＝模糊目標＋sonnet＋--experiment ab_A；B＝手寫 SDD 規格 .md 當 plan_ref＋--model haiku＋--experiment ab_B；在拋棄式 repo/branch 序列跑（勿並行同檔任務）。跑完 loop experiment ab 看兩組的 pass 率／平均 session%／attention 率／resume。
  • 放行閘門：唯有 B 組（SDD＋haiku）在 pass 率不劣、且額度顯著更省時，才把 model_routing 開起來、route_S 調成 haiku（見第 8 章）。這也是為什麼分流預設全關。
  • Epic 版：開 sdd_specs 後，tool=plan 的 Epic 規劃器會自動為每個子任務生成獨立自足規格（見第 13 章），就不必手寫 B 組規格。

19環境與部署（Environments + Deploy）

environment 欄位原本只是套用 env:<name> 知識的標籤；現在額外對到一張真正的 environments 表，把「環境」升級成一個可執行的部署目標——服務「在家開發、帶去公司部署」：home 設 auto_deploy，本機直接跑 deploy_cmd；company 不設 deploy_cmd（auto_deploy=0），改產出一份部署包＋人工檢查清單，帶去公司照做。

欄位說明
name環境名稱（主鍵），例 home／company。
kinddev／staging／prod（僅供顯示，不影響行為）。
host資訊性描述，例 linux-rtx2080／windows-11。
capabilitiesCSV，語意與 host_capabilities 設定相同（gpu,camera,os:windows,...）；任何 environment=此名稱 的一般任務，這些 token 會併入第 9 章的 V2 缺能力檢查——本機若不具備，command 驗證自動跳過、改判 manual。
deploy_cmd在 repo_path 執行的部署 shell 指令。留空＝這個環境永遠走人工部署包。
auto_deploy1 且 deploy_cmd 有值，才會自動執行；否則一律走人工。

首次啟動即播種兩筆（INSERT OR IGNORE，不覆蓋你自己的修改）：home（kind=dev, host=linux-rtx2080, capabilities=gpu, auto_deploy=1）、company（kind=prod, host=windows-11, capabilities=os:windows, auto_deploy=0）。deploy_cmd 兩者皆留白——請用 loop env add home --deploy-cmd "..." 補上你自己主機的實際部署指令。

部署任務怎麼跑（tool=deploy）

  • 不派工給 agent、不建 worktree、不跑驗證——直接解析 environment／repo_path／base_branch，記下要部署的 commit（base_branch 的 git rev-parse）。
  • auto_deploy 環境（如 home）：在 repo_path 執行 deploy_cmd；exit 0 → deployments 記一筆 deployed（含 commit），任務轉 review；非 0 → 記 failed，任務轉待確認。
  • manual 環境（如 company，auto_deploy=0）：不執行任何指令，改在 outputs/deploy-<id>/DEPLOY.md 寫一份部署包（commit、repo/base、依知識庫 env:<name> 整理的環境限制、人工部署步驟），deployments 記 manual-pending，任務轉 review「待人工部署」——帶去公司照著做，做完回來按結案。

回滾

loop deploy rollback <env> 或 POST /api/deployments/:id/rollback：找出該環境上一筆 deployed 的 commit，新增一筆 rolledback 記錄指向它；auto_deploy 環境會帶 LOOP_DEPLOY_SHA 環境變數重跑 deploy_cmd（by design 不直接動你的 checkout——要 checkout 到該 commit 由 deploy_cmd 腳本自己用這個變數處理，符合「絕不動使用者 checkout」的鐵律）；manual 環境則產出 outputs/rollback-<env>-<id>/ROLLBACK.md 人工檢查清單。

20交付 pipeline 模板（CLI／API）

🗑️/pipelines.html 已於 2026-09 移除；/api/pipelines、loop pipeline 與看板上的 pipeline 進度條都還在。

ADO 的 multi-stage pipeline 是人工寫的 YAML（build→test→deploy）、推 push 觸發；Loop 的自主版是預定義模板——一個動作就把「implement → verify → deploy」這種固定分解，實體化成一條第 13 章的 depends_on 任務鏈，每個 stage 沿用既有的驗證模式（command／llm／manual，見第 6 章）與第 19 章的部署當作自己的關卡。這不是新的執行語意，只是 depends_on + verify + deploy 的一個方便組合。

  • 模板存哪：pipelines 表（name 主鍵、def JSON），首次啟動即從 seed/pipelines/*.json 播種（INSERT OR IGNORE，不覆蓋你自己的修改，作法同第 19 章的 environments 播種）。內建三個：feature（implement → llm-gate → deploy home）、fix（implement → command-verify）、ship（implement → verify → deploy home → deploy company〔人工〕）。
  • 怎麼跑：loop pipeline run <name> --goal "…" --repo /path --base main [--env home] [--title "…"] [--verify "npm run typecheck,npm test"]，或 POST /api/pipelines/:name/run，或 MCP 的 loop_run_pipeline。goal／repo／base／verify 由每個 stage 共用（因為改的是同一份 code），各 stage 自己的 verify_mode／environment／complexity 則照模板固定。
  • 實體化：依模板順序建出一串任務，用 depends_on 串成鏈，共享一個新的 pipeline_id（+ 各自的 stage_name，如 implement／deploy-home）；第一個 stage 通過 gate 就直接 queued，其餘留 draft，交給第 13 章既有的任務鏈機制依序放行。
  • 關卡＝既有驗證模式：command stage 要跑過驗證指令；llm stage 要過 rubric（模板的 rubric_hint 會變成該任務的 verify_rubric）；deploy stage 走第 19 章的部署（環境是 auto_deploy 就自動部署，否則產出人工部署包）。任一 stage 失敗（failed）就停在原地——下一棒的 depends_on 判定為 dep-failed，永遠不會被自動派工，跟第 13 章第 3 節的任務鏈規則完全一樣，沒有另外發明失敗處理。
  • 總覽：「看板」分頁上方多一條 pipeline 進度列，例如「feature: implement ✓ → review-gate ⏳ → deploy-home ○」，點任一 stage 開該任務詳情；卡片本身也會多一顆「🚦 stage 名稱」徽章，詳情視窗列出整條 pipeline 各 stage 的狀態。
  • 自訂模板：loop pipeline list 看目前有哪些；loop pipeline import [file]（不給檔案就重新匯入內建 seed/pipelines/*.json）或 POST /api/pipelines/import 批次匯入——壞掉的 stage（缺 name、coding_tool 不合法等）該筆會被拒絕並回報原因，不影響其他筆匯入成功。
# CLI：用 ship 模板一次交付到兩個環境
npm run loop -- pipeline run ship \
  --goal "上線第三方登入" --repo /path --base main \
  --verify "npm run typecheck,npm test"
🚦Pipeline 只是幫你一次生出一條固定的任務鏈；生出來之後，續跑／重來／放棄／attention 觸發，全部跟一般任務鏈一模一樣（見第 13 章）——沒有專屬的例外處理。

21ADO/GitHub 整合橋接

D5：Loop 不取代公司的 ADO/GitHub，而是插在它上面當自主執行層——從 ADO/GitHub 拉一張 work item/issue → 建成 Loop 任務 → Loop 自主實作 → 把結果（PR 連結＋狀態）推回原 work item 留言。預設整個功能全關、零外部呼叫；只有明確設定 provider 並在環境檔案填妥憑證後才會動作。

  • 啟用：loop config set integration_provider github（或 ado；預設 none＝完全關閉，不論憑證是否存在都不會呼叫外部）。憑證只放在 ~/.config/loop-engineering/env（絕不進 SQLite、絕不進 log）：GitHub 用 GITHUB_TOKEN（＋選填 GITHUB_API_URL，支援 GHES）；ADO 用 ADO_PAT / ADO_ORG / ADO_PROJECT（三者缺一即視為未設定）。
  • 拉取（import）：loop pull --provider github --query "assignee:@me label:loop repo:owner/name"（GitHub 的 query 是 search 語法；ADO 則整段當 WIQL 查詢），或 POST /api/integrations/import，或 MCP 的 loop_pull_workitems。每個 work item 建一個 Loop 任務（標題/目標取自 item、plan 由內容合成），並記一個新的 source_ref 欄位（如 github:owner/name#123 / ado:456）——同一個 query 重跑不會重複建立（依 source_ref 判斷已存在即跳過）。建立後依 max_autoqueue 剩餘額度自動入列，其餘留 draft。
  • 推回（pushback）：任務進到 review／closed 時，若該任務有 source_ref 且 integration_pushback 設定為 true（預設 false），背景（fire-and-forget，不擋 tick）在原 work item 留言 PR 連結＋狀態；失敗只記一筆 note，不影響任務本身。
  • 看板：卡片上會看到「⇄ github#123」這類徽章（從 source_ref 解析）；點開卡片可看完整來源與最近一次 pushback 結果。
  • 測試：src/__tests__/integration.test.ts——provider 的 fetch 全部注入假實作，零網路；涵蓋 listWorkItems 解析/失敗降級為 []、import 的建立與冪等、pushResult 的留言內容、pushback pump 的旗標/憑證閘門。
🔗這條橋接完成了 ADO-surpass 藍圖 D1–D5：Loop 從獨立排程器，走到能直接吃公司既有 ADO/GitHub 的待辦，自主做完再把結果留言回去——不用手動搬 issue，也不用打開兩套系統核對進度。

一句自然語言描述（例：「大型AOI PR 最新進度 one page」）就能生成一份 OpenProject 專案報告：伺服器盡量即時查詢 OpenProject（走第 15 章 SSoT 連接器的設定），查不到才退回既有語料快照；套用可重用的「老闆範本」（persona：格式＋語氣＋詳略）或內建一頁式繁中預設，交給 LLM 合成內容。預設整個功能關閉（report_enabled=false），零行為影響——沒開之前，POST /api/report 與所有 /api/report/templates* 端點都回 404、CLI 會提示先開設定、MCP 回空報告。

  • 啟用：loop config set report_enabled true。相關設定：report_model（合成用模型，預設 sonnet）、report_budget_chars（塞進 prompt 的資料筆數字元預算，預設 4000）、report_live_first（先試即時查詢，預設 true）、report_default_template（沒指定/挑不到範本時的最後備援範本名稱，預設空＝用內建一頁式）、report_timeout_ms（POST /api/report 最長等待毫秒數，預設 100000，見下方「速度與進度回饋」）。
  • 怎麼用（Deck 頁移除前的操作，CLI／API 仍在）：report.html 曾是一頁滿版、淺色、16:9（1920×1080）的簡報式 Deck：左側控制欄填描述、用老闆範本卡（自動／廠長／經理／PM，也可從下拉選其他自訂範本）挑 persona、（選填）指定專案，按「產生報告」；右側即時排出一疊可翻頁的投影片（方向鍵／點按導覽），並可一鍵匯出 PDF／PNG／單檔 HTML／PPTX。也可以 CLI loop report generate "大型AOI PR 最新進度 one page" --template plant-manager-onepage，或 MCP 的 loop_report（template 參數選填）／loop_report_templates（列出可用範本）。
  • 專案比對精準度：描述解析出的專案關鍵詞先比對完全相符與去除括號/空白後的完全相符（例如「大型AOI」＝「【大型AOI】」），再退到子字串比對，都還有多筆同分才用 edit distance 取名稱最相近者——避免像「大型AOI」被過度簡化成「AOI」時，誤配到另一個名稱也含「AOI」的無關專案（見 src/report/opdata.ts 的 bestRowMatch）。
  • 老闆範本（persona）：report_templates 表（name 主鍵、def JSON：{name, description, audience, format, instructions, sections?, default_project?, model?}），首次啟動從 seed/report-templates/*.json 播種（INSERT OR IGNORE，不覆蓋你自己的修改，作法同第 20 章的 pipeline 模板）。instructions 是自由敘述（格式、語氣、老闆偏好、詳略），會直接取代內建預設注入合成 prompt。內建三個 persona：plant-manager-onepage（廠長一頁綜覽，極精簡，只看風險/里程碑/紅燈）、manager-pr-weekly（經理 PR/備料週報，交期/待簽核/到料表 + 進度%）、pm-detailed（PM 詳細進度，逐 work package 狀態/交期/負責人/卡點，可多頁）。
  • 沒指定範本時的挑選邏輯：只給描述、沒指定 template 時，會讓 LLM 從目前登錄的範本清單挑一個最合適的（挑不到就繼續往下退）；再退到 report_default_template 設定；最後才用內建一頁式預設——不論哪一層，指定了不存在的範本名稱一律優雅退回內建，不會報錯。描述解析（project/topic）與範本挑選現在合併成同一次 haiku 呼叫（沒指定範本、給了描述時），比舊版少一次 LLM 往返。
  • 自訂範本：loop report templates 列出目前有哪些；loop report templates add --file <json>（{"items":[...]}）批次匯入，或 POST /api/report/templates（單筆新增/更新）、POST /api/report/templates/import（批次）——壞掉的範本（缺 name/instructions 等）該筆會被拒絕並回報原因，不影響其他筆匯入成功。
  • 速度與進度回饋：整趟產生（解析＋抓資料＋合成）過去實測約 72–88 秒且看板毫無回饋；現在 report.html 按下「產生報告」後會顯示經過秒數與階段提示（解析描述中…→抓取專案資料中…→產生報告內容中…→排版投影片中…，依耗時門檻切換），並在 120 秒後自動中止顯示逾時錯誤，不會看起來卡死。後端 POST /api/report 也保證在 report_timeout_ms（預設 100 秒）內一定回應——逾時會回 504 {"timedOut":true}，而不是讓連線空等；報告本身仍會在背景跑完（report_persist=true 時照樣落地存檔）。
  • 看板頁（16:9 Deck）：report.html／report.js 把回傳的 markdown＋meta.stats（KPI 數字）＋meta.items（逐項進度）＋Mermaid 圖表，程式化排成一疊 1920×1080 投影片——封面（大標＋KPI＋LIVE/快照標）、進度總覽面板（原生進度條，逾期標紅，超過 9 項自動續頁）、各 ## 段落（條列自動依關鍵字上色、過長自動分頁）、每張圖表各一頁。依老闆 persona 換主色（廠長磚紅／經理琥珀／PM 藍）。全程 DOM API／textContent-only（Mermaid SVG 是唯一的 innerHTML 例外），且 **粗體** 以真正的 <b> 節點渲染。這一頁不依賴共用 styles.css，自帶淺色設計系統（report.css），因此列印／匯出時樣式完整。
  • 匯出（先 HTML、再存其他格式）：PDF＝window.print()＋內建 @media print（每張投影片一頁 1920×1080）；PNG＝把當前投影片經 <foreignObject> 光柵化成圖檔；單檔 HTML＝內嵌 CSS＋迷你控制器，可離線翻頁；PPTX＝本機 vendor 的 web/vendor/pptxgen.bundle.js（絕不連 CDN），每張投影片一頁全幅圖。匯出前會等圖表渲染完成，PNG/PPTX 遇瀏覽器限制會提示改用 PDF/HTML。
  • 測試：src/__tests__/report.test.ts——範本 store 的播種/匯入 idempotent、upsert、壞 def 拒絕不炸；generateReport 帶 template 時斷言選中範本的 instructions 進了合成 prompt（取代內建預設）、未知範本優雅退回內建、meta.template 正確；專案比對的多筆同含關鍵字消歧義、合併 parse+template-pick 後仍正確；路由的 templates CRUD 與逾時保證；report.test.ts/report.static.test.ts 涵蓋 report_enabled=false 的零行為變化。全程零網路/GPU/token。
📋範本只換「怎麼寫」——資料來源、即時/快照退語料、預算守護、guard 邏輯全部沿用第一版報告功能，沒有另外發明一套語意。

24報告圖表（Mermaid）與存檔

使用者回饋報告純文字太多——這一版把甘特圖／狀態圓餅圖（可選相位流程圖）加進報告，並可選擇把報告連同原始資料、圖表存到本機目錄，讓你直接抓圖貼簡報，或用自己的 git 追蹤歷史。圖表資料一律由 src/report/charts.ts 的純函式從結構化 work package 資料程式化產生，LLM 完全不碰數字——LLM 只負責寫「摘要 / 風險與落後 / 下一步」的敘述文字，不再重述甘特圖已經呈現的逐筆進度/交期表格。存檔功能預設關閉（report_persist=false），零行為影響。

  • 圖表怎麼來：只要 generateReport 抓到即時 OpenProject 的結構化 work package（source=live）就會自動附圖，不需要另開關；查不到、退回既有語料快照（source=snapshot，純文字片段沒有結構化欄位）時沒有圖可畫，meta.charts 會是空陣列。附的圖固定是甘特圖（ganttChart，依狀態或相位分 section，已結案標 done、逾期未結案標 crit，沒有任何日期的項目略過）＋狀態圓餅圖（statusPie，把每筆項目歸到「進行中／已結案／逾期／未開始」四個互斥類別中，數量為 0 的類別不畫），有兩種以上 work package 類型時再加一張相位流程圖（phaseFlow，逾期的相位標紅）。圖表以 ```mermaid 區塊附加在報告文字最後的「## 圖表」小節，回傳的 meta.charts 會列出實際附了哪些（例：["gantt","pie"]）。
  • 看板頁怎麼畫：report.html／report.js 本機 vendor 了 web/vendor/mermaid.min.js（絕不連 CDN），Deck 排到圖表投影片時才動態載入；用 mermaid.render()（securityLevel: 'strict'，只渲染我方程式化產生、經 mermaid 自身淨化過的圖）把結果 SVG 插進該張投影片的容器——這是整個看板唯一用 innerHTML 的地方，其餘全部維持 textContent-only（有靜態測試守著這條界線）。每張圖獨立成一頁（## 圖表 以及任何 ## 段落底下的 mermaid 區塊都會被收集渲染）；渲染失敗會退成原始碼區塊，不會炸掉整份 Deck。
  • 存檔（report_persist / report_output_dir）：預設 report_persist=false——不開就完全不寫檔。開啟後（或單次呼叫加 save），每次成功產生報告都會把 (a) 報告 markdown、(b) 這次的結構化 work package 快照 JSON、(c) 每張圖表各自的 .mmd 原始碼，分層寫到 report_output_dir/<專案>/<YYYY-MM-DD-主題>/（report_output_dir 預設 <資料目錄>/reports，即 ~/.local/share/loop-engineering/reports）。純寫檔，不會自動 git commit——目錄結構是為了讓你自己的 git 好追蹤/好找；寫檔失敗只會記一筆錯誤，不影響報告本身的產生與回傳。
  • 怎麼觸發存檔：loop config set report_persist true 讓之後每次產報告都自動存；或不改設定、單次 CLI 加 --save：loop report generate "大型AOI PR 最新進度" --save（印出寫了哪些檔案路徑）；看板頁表單也有「同時存檔」勾選框；POST /api/report 的 body 加 {"save": true} 效果相同。有實際寫檔時，CLI/API 回傳都會多一個 files（絕對路徑陣列）。
  • 測試：src/__tests__/report.charts.test.ts（純函式：合法 Mermaid 語法、逾期標 crit、已結案標 done、特殊字元跳脫、空輸入回空字串）、report.persist.test.ts（注入假 mkdir/writeFile：分層路徑、三種檔案、寫檔失敗回 null 不炸）、report.test.ts（generateReport 附圖與 meta.charts、report_persist/save 的持久化開關）、report.static.test.ts（report.js 除 mermaid 容器外只有一處 innerHTML、securityLevel: 'strict'、無外部載入〔僅 /vendor bundle，唯一的 http 字面量是 w3.org 命名空間〕、本機 vendor 了 mermaid＋pptxgenjs、頁面自帶 report.css 不依賴 styles.css、四個匯出鈕與 persona 皆在、report.css 有 1920×1080 canvas 與每頁 1920×1080 的 @media print）。全程零網路/GPU/token。
📊圖表只是把已經在算的資料（甘特/狀態計數）換一種呈現方式——沒有另外呼叫 OpenProject 或另外花 token，也不影響第一版報告功能（即時查詢/快照退語料/老闆範本）的任何邏輯。

25企業週報 PPTX（公版格式）

公司要的不是「AI 排版的簡報」，是「填進公版格式、人眼一眼認得出來的週報」——所以這條線徹底反過來做：LLM 只產出結構化 DeckSpec JSON（status 文字／說明頁敘述），版面本身一律由 scripts/report_pptx.py 對公版模板做確定性 fill-only 渲染，絕不在執行期生成版面、複製投影片或調整位置。四條任務鏈（T1 模板+渲染器、T2 週組裝+人工把關、T3 LLM status+品質閘門、T4 這裡：一鍵命令＋REST＋MCP＋本文件）都已合併進 main。預設整個功能關閉（report_pptx_enabled=false），零行為影響——沒開之前，loop report pptx/weekly * 直接印提示 fail-fast，POST/GET /api/report/weekly* 一律回 404，MCP 的 loop_report_weekly 呼叫會失敗並附帶錯誤訊息。

功能總覽

  • 公版 fill-only 渲染：模板製作期把公版原型頁複製成固定容量的 pool（1 頁總表＋N 頁主頁＋N×2 頁說明頁，見下方「模板製作」），渲染器只認 shape 名字（LOOP: 慣例）把值填進去或清空，絕不在渲染時期新增/刪除投影片或改版面座標。
  • 黑／藍／紅確定性上色規則：每個 status 項目跟上週實際出貨的 deck-spec.json 做純函式 diff（src/report/pptx/diff.ts）——文字完全相同＝black（沿用中）；新出現的文字＝blue（新增）；人工手動標記的＝red（需高層關注，一旦手動標紅就不會被自動重新分類覆蓋）。這條規則在 render／run 階段每次都會重新計算，所以就算你手改了 status 文字，顏色仍會正確反映「這段文字跟上週比是不是新的」。
  • 品質閘門（Skywork 對標）：LLM 生成 status 候選後，先跑一次 haiku 潤稿（文法/贅字/壓成單行），再用 llm_judge_model 依「綜合評分／有無引用進度佐證（work package 來源）／潤稿完成度」評分；沒過就帶著 judge 的 feedback 重生一次再評一次，仍不過就標成 quality_flags（提醒把關時特別確認）——閘門只標記，絕不擋出片，最壞情況就是全黑沿用上週內容，不會開天窗。
  • 人工把關流程：說明頁（explain pages）永遠先落在 explain-pages.json，欄位 approved:false 起跳；render／run 只有在該檔案 approved:true（或明確帶 --allow-unapproved）時才會把說明頁塞進 deck，符合公版「上週的說明頁拿掉、只放當週新批准的」規則——這條把關線一鍵指令也不會繞過：週目錄全空時第一次 run 一定是 0 頁說明頁＋一則 warning，等你編輯批准後再 run 一次才會真的進 deck。

前置：模板與資料維護

  • 模板放哪：定案的 fillready.pptx＋manifest.json 放進 <report_pptx_dir>/template/（或用 report_pptx_template／report_pptx_manifest 指向任意路徑）。公版原始檔案（含真實公司格式的 .pptx）本身是公司機密，絕不進 repo，只有渲染器需要的兩個衍生檔案會落地。

本地模型怎麼跑

  • 選模型：任務的 Model 選 local:<id>（新增任務對話框、loop add --model local:qwen38-flash、MCP loop_add_task），或把設定裡的 Coding 預設模型改成 local:…。
  • 執行：引擎用 opencode run --format json --auto 驅動 vLLM 的 OpenAI 相容 API，走同一套 worktree、驗證、續跑與 Git 收尾。設定以 OPENCODE_CONFIG_CONTENT 帶入（不寫進 repo），並禁止 git push、sudo、網路抓取。

  • 逾時：本地解碼較慢，依複雜度的預設逾時會乘上 local_timeout_multiplier；任務自己指定的 timeout 不受影響。

寫 PRD：工作流程（/flow.html）

要讓模型改好軟體，PRD 必須講清楚三件事：原始碼在哪（repo／分支）、要改什麼（症狀→期望、相關檔案）、怎麼驗證。原本的五步驟「PRD 精靈」已經併進工作流程（見第 5a 章）：這三件事攤在需求、準備環境、驗證、驗收門檻、人工核可這幾個節點上，缺什麼那個節點就亮 ⚠。草稿自動存在伺服器（依「你是」分開），開始頁的「最近的草稿」可以接著寫或刪掉；已經建成任務的草稿刪掉後任務仍然留著。對話裡任一則回答按「轉成任務」，選項是「開問題單／留待辦」：開問題單會帶著問題、回答摘錄與截圖開一張問題單（見第 5b 章）。

PRD 閘門：先把需求寫完整，再交給本地模型

  • 入口：工作流程（一步步填，或在開始頁「貼上 PRD」；按「檢查」→「開始執行」）、對話操作、loop prd check|submit <檔案>、MCP loop_prd_check / loop_prd_submit。範本：loop prd template，建議貼給 Opus／Fable 請它照這個格式寫。
  • 第一關（規則，必過）：必須有標題、目標、範圍、非範圍、驗收標準、可執行的驗證指令、存在的 Repo 路徑與合法領域；還留著範本佔位文字（<…>、TODO、TBD、待補）一律擋下，並逐項列出缺什麼。
  • 第二關（本地模型審查，零 token）：由目前載入的本地模型以「不能反問的實作者」角度讀 PRD，指出會讓它猜測或無法驗證的地方；它判定不可行時同樣擋下。模型沒有載入時預設只看第一關，設 prd_require_llm=true 則改為擋下。
  • 通過後：PRD 原文存成任務的 plan，驗收標準成為驗收 rubric，任務以 prd_default_model（沒設時用 local:… 的 default_model）排入佇列；勾選多個模型則直接建成 Benchmark。

Benchmark：同一題交給多個模型各做一次

評比頁（/benchmarks.html，左側導覽的「評比」）有四個部分：每一場、快篩（見下一節）、戰績，以及單場的詳細頁（#b=<id>）。按標題列的「＋ 新評比」進到建立流程。

  • ① 題目四種來源：
    • 看板任務（預設）：沿用那張任務的 repo、計畫與驗證指令；缺 repo 或計畫的任務會標「缺 …」，選了也不能送出。
    • 工作流程草稿：工作流程寫好的草稿，送出前照樣過 PRD 閘門。
    • 自己出題：看板上沒有這張任務、但臨時想比一題時用——填標題、目標、現有 repo 的路徑與驗證指令，系統照這份描述幫每個模型各開一張任務。表單沒有「計畫」欄位：系統會把這份題目本身寫成一份計畫檔（plans/bench-*.md）給每一組看，評比若被擋下來那份檔案也會一併刪掉。可以另外選一個驗證方案：驗證指令（依機台自動加上 sandbox:）、驗收指標、保護路徑、產出物與 setup 都照方案，repo 沒填就用方案的——每一組用同一把尺。
    • 內建題庫（seed/bench/*.json，放在最後）：slugify、LRU cache、CSV 解析、token bucket、二值化＋連通元件、log 分析——練習用的中性小題，各自附 tests/ 當驗收（python3 -m unittest discover）。每次評比會在 spike_root/.bench/ 開一個全新的 repo（含自己的 bare origin），不碰任何現有專案。第一次試用評比、或只想比「純寫程式能力」時才用。
  • ② 參賽模型（至少 2 個）：本地模型直接從模型目錄來，跑不動的會灰掉並寫原因（權重沒下載、映像沒建、需要 2 台 Spark）；雲端模型（Sonnet／Opus／Haiku）會標「花訂閱額度」。
  • ③ 評審（可多選）：每位雲端評審各評一次，看每組的驗證結果與 diff（每組最多 bench_diff_cap_chars 字），依正確性／完整性／程式品質／遵循度各給 0–10 分。組別以 Arm A/B… 匿名。多位評審時，每項分數取平均後重新排名，並標出評審一致或評審分歧；某位評審失敗不影響其他人（全部失敗才算「評分失敗」）。評審也會看到驗收門檻、每一組每次驗證量到的指標、有沒有自己用 ncu，以及最終量測。排名先看有沒有通過門檻：沒通過的組不管分數多高，都排在通過的組後面；沒有任何一組通過就沒有勝出者（也不記勝場）。
  • 量測型評比（有驗收指標時，例如 CUDA 要壓在幾 ms 內）：
    • 迭代：每一組的每次驗證都留下紀錄。詳細頁與報告的「迭代」欄寫出第 1 次就通過、第幾次才通過（先前是功能沒過，還是功能對了但指標沒達標——「先對功能、再調效能」），或都沒通過；還有這個模型工作時自己在 GPU 沙盒試跑了幾次、有沒有自己跑 ncu／nsys。驗證沒過時引擎會把原因（含沒達標的指標）送回給模型再試，最多 max_resumes＋1 次。
    • 最終量測（bench_final_measure，預設開）：所有組都結束後、評分之前，引擎用同一套驗證指令一組一組重新量一次各組的最終程式——避免某組自己量的時候剛好和別組的編譯或本地模型搶 GPU。排名、通過率都以最終量測為準；各組自己量到的數字留在迭代紀錄裡。
    • 報告：詳細頁的「下載報告」（或 loop bench report <id>）產生一份 Markdown：結論、總表（最終量測、每個門檻指標、迭代、評分、token、耗時）、各組的迭代紀錄與評語，以及這類工作所有模型的累積戰績。
  • ④ 送出前會估時間（切換本地模型的次數 × 每次幾分鐘 ＋ 各組實作 ＋ 評分），並列出會花訂閱額度的次數（雲端參賽組＋評審人數）與目前的 session／weekly 用量；用量偏高時會直接警告。
  • 一次只能有一個評比：一台 Spark 只有一顆 GPU，兩個評比同時跑會互相搶模型，而且只有一個看得到。已經有評比在跑時，建立頁會直接說「已經有一個評比在跑：…」。
  • 取消與刪除：詳細頁的「取消評比」會把還沒跑完的組別停掉並標成失敗，把機器讓出來；跑完之後可以「刪除這次評比」，只移除這次比較，每個模型跑出來的任務會留在看板上。若某一組的任務被刪掉，那一組就不列入評分（剩不到兩組時整個評比會標成已取消）。
  • 執行：每個模型是一張普通任務（標題 [bench] …），各自的 worktree、驗證與續跑，但永遠不會合併回 base branch。一台 Spark 一次只載入一個模型，所以本地組會輪流切換；評比進行中，對話頁右欄的「模型」分頁會顯示「評比使用中」並鎖住切換鈕，評分完成後自動切回原本的模型。
  • 結果：推播一次；評比頁的模型 × 領域矩陣累積通過率（有最終量測就看最終量測）、一次就過率、平均第幾次才過、自己用 ncu 的比例、平均分數、勝率、平均輸出 token 與耗時，可依軟體類型、本地／雲端、最低通過率、最少場數篩選。上方的「各類工作建議的本地模型」替每種軟體類型挑出通過率最高的本地模型（同分再比一次就過與評分），旁邊列最好的雲端模型當對照，並寫一句結論（可以交給本地、做得到但不如雲端、還做不來）；少於 3 場只能當參考。評比後 arm 的 worktree 會清掉，loop/<任務 id> 分支保留供檢視；之後重新評分也會沿用當時的量測與 diff。
  • 花費：評審是一個 benchmark 唯一的 Anthropic 花費（每位評審一次 claude -p），除非你讓雲端模型也參賽。用量達硬上限時會延後並標為「評分失敗」，可在詳細頁按「重新評分」或執行 loop bench judge <id>；已評分的評比也可以重新評分（會再花一次額度）。服務若在評分中途重啟，下一輪 tick 會自己把它接回去評完。
  • 工作流程的 AI 實作節點選 2 個以上模型，就把同一份 PRD 送成評比。

模型快篩：用小題先驗很多模型

一場完整評比要好幾個小時；新模型很多、要一個一個驗時，先用快篩看它會不會寫程式、懂不懂工具，再決定要不要進正式評比。快篩不評分、不做最終量測、不花訂閱額度。

  • 怎麼開始：評比頁的「快篩」分頁勾一個或多個本地模型，預設題目是內建題庫的 slugify、log-analyzer、csv-parser，每題上限 15 分鐘；也可以在對話說「快篩 gpt-oss-120b」，或 loop bench screen --models local:a,local:b。只有「模型」分頁登錄過的本地模型能快篩（第一次切換某個 recipe 就會登錄）。
  • 怎麼跑：每個「模型 × 題目」是一筆快篩，同一批共用一個 sg_… 編號。依模型分組、一題接一題跑，每個模型只切換一次；每題的時間從開始寫程式才算，切模型的時間不算，超時就結束那一題。
  • 排隊：快篩也遵守「一次一場」，會排在正在跑的評比後面；排程暫停時不會開始。整批跑完推播一次，並切回原本的模型。
  • 看結果：快篩分頁每批一張卡：每個模型每題「通過（第幾次）・幾分」或「沒過」與原因。總覽的流程圖把一批畫成「快篩 → 題1 → 題2 → 結果 x/y」。可以取消整批，跑完的批次可以刪除。
  • 戰績：快篩的通過率、第一次就過、時間會算進戰績；勝率、評審分數、兩兩對戰只看正式評比，互不干擾。戰績可以切「含快篩」；某個模型只有快篩結果時，推薦會寫「只有快篩結果」。

分頁列出 spark-vllm-docker/recipes/ 裡每一個 recipe（不只註冊過的五個），並依這台機器的現況決定每一列唯一的下一步。一台 Spark 其實能跑二十來個 recipe，卡住的通常只是兩件事：權重還沒下載、或它們共用的容器映像 vllm-node 還沒建——這兩件都能在面板上一鍵完成，在背景跑、一次一件、不影響正在服務的模型。

按鈕什麼時候出現做什麼
切換權重完整、映像已建、台數夠先跳確認，再重啟 vLLM（幾分鐘、期間不能對話）。第一次切某個 recipe 會自動把它登錄進 local_models（id＝recipe 檔名），之後對話與 Benchmark 的模型清單也選得到。
下載（≈NN GB）／續傳權重不在 HF 快取，或下載到一半背景跑 uvx hf download <model>（可續傳；大小來自 HF API，快取一天）。進度條顯示已下載 GB／總量與 log 最後一行，可取消——下載到一半的檔案留著，再按一次會續傳。
建置 vllm-node有模型已下載但映像沒建只出現一次（上方提示卡，寫著幾個模型在等它）。vllm-node／vllm-node-b12x 其實是拉現成映像再 tag（約 24 GB：有線幾分鐘，這台走 Wi-Fi 實測約 5 MB/s、要 1 小時多）；vllm-node-mxfp4 要真的編譯，20～40 分鐘。跑的是 run-recipe.sh <recipe> --solo --build-only。
灰字需要 2 台以上 Spark、配方缺 model 欄位、或 HF gated 模型（這台沒有 HF token）不給按；第二台接上後照下面的「兩台 Spark」設定。

推薦三張卡固定是：對話＝Qwen3.8 Flash Next、寫程式＝Qwen3 Coder Next（int4）、小而快＝Qwen3.6 35B NVFP4；「全部模型」收合區依 可切換／可下載／需要建置映像／需要 2 台以上 Spark 分組，並顯示磁碟剩餘空間。

用途標籤：不只推薦那三張，清單裡每一列名字前面都有一個標籤——對話／寫程式／小而快／看得懂圖／會推理／大模型，滑鼠移上去有一行說明。標籤由配方本身的事實自動判定（model id 含 Coder、含 Vision、配方名含 thinking、HF 回報的權重大小、參數量、需要幾台 Spark），所以上游 spark-vllm-docker 新增配方時不必改 Loop 就會有標籤；少數判錯的（例如 106 GB 但其實是日常對話模型的 Qwen3.8 Flash Next）寫在 src/local/catalog.ts 的 ROLE_OVERRIDE 覆寫表裡。標籤只說「這個模型是幹嘛的」，不代表推薦——推薦區仍然只有精選的三張，意思是「這台現在按下去就能跑」。

⚠️三道擋下來的檢查（都在伺服器端，不只是畫面上灰掉）：台數不夠、權重沒下載完（blobs/*.incomplete 存在就算沒下載完）、容器映像還沒建置。最後一項是真實事故：切換時 run-recipe.sh 會先停掉目前的模型，再問「Build now? [y/N]」，在無人互動的環境拿到 EOF——結果舊模型停了、新的起不來。現在會直接回 409，目前正在服務的模型完全不受影響。另外下載不走 run-recipe.sh --download-only：它看到 snapshots/ 非空就當作已下載，中斷過的下載永遠不會被續傳。

回答產生中不給切換；切換後畫面每 5 秒回報狀態（starting／ready／error）與已經過的分鐘數，對話紀錄不受影響。工作狀態存在 local_job_json，引擎重啟後會依 pid 重新認領還在跑的下載；log 在 <data>/logs/local-<download|build>-<recipe>-*.log。CLI：loop local download <recipe>、loop local build <recipe>、loop local jobs。

API：GET /api/local/catalog（每個 recipe 的 action／size／blocked_by＋images＋job）、POST /api/local/catalog/:recipe/load、POST /api/local/jobs {kind: download|build, recipe}（409 已有工作／507 磁碟不足）、GET /api/local/jobs/current、POST /api/local/jobs/current/cancel、GET /api/local/jobs/current/log?lines=40。

兩台 Spark：跑一台放不下的大模型

兩台 DGX Spark 用 200G 網路對接後，需要兩台的 recipe（配方裡寫 cluster_only: true）就能載入。Loop 的做法：

  • 啟動：local_spark_nodes 是 2、而且配方需要兩台時，改用叢集模式 run-recipe.sh <recipe> --earlyoom（不加 --solo），節點由 vLLM repo 的 .env 決定。單機配方照舊用 --solo。
  • 停止：local_spark_nodes 是 2 時，每次切換模型或 loop local stop 都會先跑 launch-cluster.sh stop 把兩台的容器都停掉，再停本機，不會留一半在另一台佔記憶體。
  • 擋下：local_spark_nodes 還是 1 時，需要兩台的模型一律灰掉、伺服器也拒絕載入。

設定步驟（第二台 spark-02 已完成基本設定、兩台用 200G 的 enP2p1s0f0np0 對接）：

  1. 網路：兩台的 200G 介面設固定 IP（這台 192.168.177.11，spark-02 192.168.177.12，MTU 9000），彼此 ping 得到。
  2. SSH：這台能免密碼 SSH 到 spark-02（ssh-copy-id）。
  3. vLLM repo 的 .env：CLUSTER_NODES=192.168.177.11,192.168.177.12、ETH_IF、IB_IF 填 200G 介面與 RoCE 裝置名稱；launch-cluster.sh --check-config 要找到兩個節點。
  4. 映像與權重：spark-02 也要有同一個容器映像與模型權重（同樣的 HF 快取路徑）。模型分頁的「下載」下載到這台；需要兩台的模型下載完成後，會自動接著跑一個同步工作（sync，scripts/sync-weights.sh），把這個模型的 HF 快取資料夾複製到 .env 的 CLUSTER_NODES 裡的其他台（權重檔本體一起複製，不是只複製連結；走 200G 約十幾分鐘）。取消的下載不會接著同步；取消同步時，已複製的檔案留著，再按一次會接著同步。切換到兩台的模型之前，Loop 會先問另一台有沒有權重；沒有就拒絕切換並說「另一台 Spark 還沒有這個模型的權重」，模型分頁會問「現在同步到另一台嗎？」，按下去就開始同步（API：POST /api/local/jobs，{kind: 'sync', recipe}）。
  5. 告訴 Loop：loop config set local_spark_nodes 2，然後在「模型」分頁切到一個兩台的模型；切回單機模型時，確認兩台的容器都停了。

這台（head）另外跑著桌面、Loop 與 vLLM 的 API 伺服器，可用記憶體比 spark-02 少約 6–7 GiB，而且沒有 swap；容器裡的 earlyoom 在可用記憶體低於 512 MiB 時會砍掉 vLLM。知識庫檢索用的 embedding 模型（bge-m3）也跑在這台，第一次查知識庫時啟動，約佔 2.4 GB GPU 記憶體加 1.5 GB，閒置 10 分鐘才結束。所以剛好塞滿兩台的模型不適合當日常對話模型：例如 GLM-5.3 Flash 照原配方載入就失敗；縮小 KV 快取與上下文的「GLM-5.3-Flash-NVFP4-Spark (精簡版・限純問答)」（vLLM repo 的 recipes/glm-5.3-flash-kv4g.yaml：KV 2G、上下文 128K、最多同時 2 個請求）能載入、也答得比 Qwen3.8 準，但一用「引用知識庫」或「上網／工具」（GPU 沙盒）就會記憶體不足而停掉，只適合把這兩個都關掉做純問答測試。挑兩台的模型時，這台要留約 4 GB 給 embedding。

對話工作台（首頁 /）

  • 入口：網址根目錄就是對話（舊的 /chat.html 會自動轉過來，?token= 保留）。直接和 vLLM 目前載入的本地模型對話，不經雲端、不花 token；需要 local_models_enabled=true 且模型狀態為就緒。
  • 速度：每則回答下方標出首字延遲、輸出速度（tok/s）、輸出與讀入 token、總耗時；右欄「模型」分頁的「機台狀況」放大顯示，生成中另有服務端即時 tok/s。「思考模式」晶片會先推理再回答，較慢，思考過程可展開。每個模型開關思考的方式不同，Loop 依模型內附的對話模板自動選：Qwen、Nemotron 用 enable_thinking；GLM-5.x、gpt-oss 沒有「不思考」可選，關閉時改用低推理強度（仍會先簡短想一下）；DeepSeek V4 用它自己的 thinking 開關。對話標題與知識庫的關鍵字擴展也照同樣規則。
  • 模型與記憶體：右欄「模型」分頁的「機台狀況」顯示權重檔大小、量化格式、MoE 架構、最長上下文、MTP 推測解碼接受率；統一記憶體已用／總量與 vLLM 上限（gpu_memory_utilization）、KV 快取容量與使用率、GPU 溫度／功耗，每秒更新（右欄收起或切到別的分頁時停止查詢）。
  • 對話紀錄：存在伺服器、依使用者分開。身分優先取 Tailscale 注入的登入帳號，沒有就用標題列「你是」填的名字（x-loop-user）。這是工作區分隔、不是權限控管：知道網址與 token 的人都看得到這台機器上的資料。可搜尋（中文兩字詞也搜得到）、改名、刪除；接續舊對話時只會把最近 chat_context_turns（預設 12）輪帶進模型，較早的內容留在畫面上並標示。
  • 逐則動作：滑過訊息會出現按鈕——重答（丟掉這個回答重問，舊的軟刪除、順序不亂）、編輯重問（把問題放回輸入框，之後的內容一併移除）、複製、存進知識庫、轉成任務、請雲端複核。

  • 智慧調整參數（右欄「調參」分頁，Alt+2）：填症狀（可加機台／模組，例「IP 瑕疵偵測」）→ 按「產生建議」，問題照樣走一般對話、回答出現在對話區，分頁上方顯示最新建議（第一條建議的檔案、參數、目前值 → 建議值、風險）與「在對話中查看」；要做成任務，用那則回答底下的「轉成任務」。下方歷史建議列出你在所有對話裡拿到的建議、對應任務與任務目前狀態，點一下就回到那段對話並捲到那一則（GET /api/chat/tune/history）。

  • 存進知識庫：把回答寫成 vault 筆記並立刻建索引，之後對話查得到；同一則回答只會存一次。需要先用 loop ingest add --vault <路徑> 登錄一個 vault 來源。
  • 請雲端複核：把這則本地回答送給雲端高階模型複核（指出錯誤、補遺漏、給最終建議）。預設關閉（chat_escalate_enabled=false），因為這是頁面上唯一會離開本機、花訂閱額度的動作；開啟後仍受 hard_limit_pct 同一道預算閘門管制，逾時 chat_escalate_timeout_ms（預設 240 秒；實測一則短回答的複核約 112 秒。連線若先斷掉，複核仍會在背景完成並存起來，重新整理就看得到）。複核結果以雲端樣式另存一則訊息，不會被帶進後續提問的上下文。
  • 存檔（單則回答）：每則回答下方的「存檔」列出這一則實際產生的東西：Markdown（模型原始文字）、HTML（排版後、只含這一則）、列印／存成 PDF（開瀏覽器列印，目的地選另存 PDF）、簡報 .pptx，以及每一段 ``` 區塊各自成檔——SVG 圖存 .svg、產生的網頁存 .html、程式碼依語言給副檔名。沒有圖就不會出現圖那一列。檔案一律下載到你的裝置，伺服器不留檔；要留在機器上請用「存進知識庫」。
  • 簡報（.pptx）怎麼來的：回答的 markdown 在伺服器切成投影片（src/chat/pptx.ts：標題成頁、條列成點、markdown 表格成真表格、每段程式碼一頁、每張 SVG 轉圖一頁），再由 scripts/answer_pptx.py 用 python-pptx 畫成 16:9。不是第 25 章那條企業週報管線（那條要公司範本，版面不可自由生成）。需要一個裝了 python-pptx 的 python：設定 office_python（空白時依序退回 report_pptx_python、資料目錄下的 office-venv/bin/python、python3）。這台已指向 office-venv；沒有的話「簡報」那一列會變灰並寫出原因。上限：40 頁、每頁 7 點、程式碼 22 行、表格 12 列。
  • 匯出與分享（整段對話）：標題列「⋯」可匯出 Markdown（伺服器產生，含出處與已轉任務／已存 KB 的註記）或 HTML（目前畫面）；「建立分享連結」會產生 /share.html#s_… 唯讀頁並複製到剪貼簿——網址裡的代碼就是憑證，任何拿到的人都看得到（不含圖片），可隨時「取消分享」立即失效。chat_share_enabled=false 可整個關掉。
  • 貼圖提問：在頁面任何地方按 Ctrl+V 貼上截圖，或拖放、按「加入圖片」（一次最多 4 張，自動縮到長邊 1600 px）。圖片存在伺服器（<data>/chat-images/），資料庫只存路徑；回放的舊圖只供檢視，不會再送進模型。
  • HTML / SVG 直接顯示：回答以 Markdown 排版；```html、```svg 或整段 <svg> 寫完後直接顯示預覽（高度上限 2400px，可按「放大」用整個視窗看），可切換「原始碼」或複製。預覽跑在沙箱內，讀不到本頁與 API token，也不能連網（只允許載入 jsDelivr / cdnjs 的程式庫）。
  • 引用 CF-AOI 知識庫：開啟後每個問題會先用混合檢索（全文＋bge-m3 向量）找出最相關的 8 段資料，放進提示讓模型依據回答並標出處編號 [1]、[2]。檢索前會先請本地模型把問題轉成 3–8 個關鍵字——因為全文索引把整句問題當成一個片語比對，口語問句幾乎搜不到，關鍵字才搜得到程式碼裡的名稱；回答下方可展開每則參考資料的檔案、行號與原文。知識庫沒有的內容模型會說沒找到。需要 rag_enabled=true。
  • 與 vLLM 共用 GPU：DGX Spark 上 vLLM 佔去大部分統一記憶體，向量化程式可用 LOOP_EMBED_DEVICE=cuda、LOOP_EMBED_MAX_SEQ_LEN=1024、LOOP_EMBED_BATCH=4 限制用量（實測 48 段長文件 28 秒、峰值約 5.8 GB）；不設定時維持原本行為。
  • 送出與長回答：Shift+Enter 送出、Enter 換行。單次輸出上限 12,000 tokens（思考模式 16,384）；寫到上限時訊息下方會出現「繼續產生」，模型從中斷的字元接著寫進同一則回答。
  • 停止：按「停止」或關掉分頁會中斷 vLLM 的生成；單次回答最長 10 分鐘。已寫出的內容仍會保存。

26a上網／工具、MCP 與終端機

三件都是「本地模型 ＋ 這台機器」的延伸：讓模型能查最新資料、能讀 repo 與 PR，讓工程師不用離開頁面就能開 shell。三件預設都關；開了也只在你明確要求時才動作。

上網／工具（composer 的「上網／工具」晶片）

模型本身不會上網——「上網」是工具。勾了晶片，這一題會把兩個工具交給模型（vLLM 的 tool calling，兩個 recipe 都已帶 --tool-call-parser）：

工具做什麼限制
web_search問自架的 SearXNG（deploy/searxng/，只綁 127.0.0.1:8080，聚合 Google／Bing／DDG，不經第三方 API、不用 key）。回傳 5 筆標題／網址／摘要。15 秒逾時。
fetch_url讀一個公開網頁，HTML 轉純文字給模型（約 12,000 字）。只允許 http(s)、2 MB、3 次轉址；內網一律擋：10/8、172.16/12、192.168/16、127/8、169.254/16、100.64/10（tailnet）、IPv6 本地位址，每一跳轉址都重新檢查；唯一豁免是 SearXNG 那個 host:port。

終端機（對話頁標題列 ⌨，或 Ctrl+`）

  • 誰看得到：terminal_enabled=true 且你的身分在 terminal_allowed_users（CSV：ts:<Tailscale 登入>、name:<名字>（只有信任的 LAN 才用）、local）。其他人連按鈕都沒有；伺服器端也擋（404／403）。
  • 怎麼用：底部抽屜、可拖高、多分頁（＋／✕、雙擊改名）。「收起」只是把抽屜藏起來，shell 還在；重新打開會接回原本的畫面。斷線自動重連。閒置 terminal_idle_min（30）分鐘自動關。
  • 開在哪裡：新分頁一律開在 terminal_cwd（預設＝Loop Engineering 這份 checkout），分頁列上會寫出路徑。這是起點不是牢籠：pty 不是沙箱，shell 仍然可以 cd 到這個 unix 使用者能到的任何地方。要換起點：loop config set terminal_cwd /path/to/repo（留空＝家目錄）。
  • 每個人有自己的 worktree（terminal_worktree=true，預設開）：第一次開 shell 時，系統會用 terminal_cwd 這個 repo 幫這個身分切一份專屬 worktree（terminal_worktree_root，預設 ~/Addis/loop-worktrees/<身分>，分支 desk/<身分>），shell 直接開在那裡，畫面第一行會寫出路徑與分支。同一個人下次再開就是同一份，不會重切。主 checkout 完全不動（git worktree add 不碰 HEAD、索引或既有分支），所以引擎自己的任務不會因為別人在改程式而把自動合併退成 pending。別人要交東西回來就正常 push desk/<身分> 或開 PR。
  • 建不起來就照常開 shell：git 壞掉、目錄不是 repo、磁碟滿了——都只會退回 terminal_cwd 並在畫面上寫原因，不會讓你開不了終端機。預設分頁（看 log）不會建 worktree，一律開在 repo 根目錄。不用的 worktree 用 git worktree remove <路徑> 清掉；關掉這個行為是 loop config set terminal_worktree false。
  • 預設分頁：模型面板工作卡的「看 log」會開一個 tail -f 該工作 log 的分頁；另有 vllmlog（docker logs）、enginelog（journalctl）。頁面不能自己指定任意指令。
  • 安全：shell 的環境變數已拿掉 LOOP_API_TOKEN；只稽核誰／何時／哪個 shell（terminal_sessions 表），不記錄鍵盤與輸出；xterm.js 放在 web/lib/xterm，不靠 CDN。
  • 啟用：loop config set terminal_enabled true、loop config set terminal_allowed_users ts:you@example.com。

API：GET /api/terminal/access、GET /api/terminal/sessions、GET /api/terminal/ws（WebSocket，token 走 ?token=）。

26bGPU 執行沙盒：自己跑、自己驗證

沒有沙盒時，對話頁的模型只有唯讀工具，寫得出程式卻只能請你「跑完把輸出貼回來」；Claude 跑任務時 Bash 也只開 git／npm／node／ls／cat，不能編譯、不能執行。沙盒補上這一段：每次執行開一個用完即丟的 Docker 容器，可以用 GPU、其他什麼都不能碰，模型與 agent 就能自己寫檔、編譯、執行、量測，以真實輸出為準。

隔離方式（每一次執行都一樣）

項目設定
網路--network none：連不到外網、內網、Loop API 與這台機器上的任何服務。套件要先做進映像。
檔案只掛一個資料夾到 /work：對話頁＝這個對話專屬的 <資料目錄>/exec/chat/<對話 id>；任務＝這個 run 的 worktree。根目錄唯讀（--read-only），/tmp 是 2 GB 的 tmpfs。
權限以引擎的 uid 執行（不是 root）、--cap-drop ALL、no-new-privileges。
資源exec_memory（16g）、exec_cpus（8）、exec_pids（512）；同時最多 exec_max_concurrency（2）個容器。
時間每次預設 exec_timeout_sec（120 秒），呼叫時可加長到 exec_max_timeout_sec（900 秒）；逾時用 docker kill 收掉容器。
映像exec_image（預設 nvidia/cuda:13.0.3-devel-ubuntu24.04，arm64 可用）。不會自動下載（--pull never）：沒有就直接報錯並告訴你要 docker pull 什麼。

啟用步驟

  1. 準備映像：docker pull nvidia/cuda:13.0.3-devel-ubuntu24.04。版本請對齊 nvidia-smi 顯示的 CUDA 版本（驅動要夠新）；要換就 loop config set exec_image <映像>。
  2. 健康檢查：loop exec check --profile。逐項列出 ✅／❌／⚠️；任何 ❌ 都附修法。
  3. 要用 ncu（Nsight Compute）量測：GPU 效能計數器預設只有系統管理員能讀，會出現 ERR_NVGPUCTRPERM。建議在主機設定驅動參數後重開機：
    echo 'options nvidia NVreg_RestrictProfilingToAdminUsers=0' | sudo tee /etc/modprobe.d/nvidia-profiling.conf
sudo update-initramfs -u && sudo reboot
    不想動主機的話可以 loop config set exec_profiling_cap true（容器多拿 SYS_ADMIN，隔離會變弱，不建議長期開）。映像裡沒有 ncu 時，loop exec check 會標 ⚠️，請自建含 cuda-nsight-compute 的映像。
  4. 打開：loop config set exec_enabled true。對話頁還要把允許的人加進 exec_allowed_users（格式同 terminal_allowed_users：ts:<登入>、name:<名字>、local；空白＝對話頁沒人能用）。

對話頁

  • 勾「上網／工具」、exec_enabled=true、你的身分在 exec_allowed_users、而且是存下來的對話——四個條件都成立，這一題才會多四個工具：sandbox_write_file、sandbox_run、sandbox_read_file、sandbox_list。
  • 模型會自己寫檔、編譯、執行、跑 ncu，再依實際輸出回答。這種題目的回合數與時間放寬為 exec_chat_max_rounds（10 輪）與 exec_chat_wall_ms（15 分鐘）；同一個指令改完檔再跑一次不算「重複呼叫」。
  • 回答下方的「工具呼叫」卡片，每次執行都有「指令與輸出」可以展開，看到的是原始輸出，不是模型的轉述——驗證結果以這裡為準。
  • 刪除對話時，它的沙盒資料夾一起刪；loop chat prune 也會清掉。

任務（Claude 與本地模型）

  • exec_enabled=true 時，每個 run 會多一個 MCP server loop-exec，只有一個工具 run（Claude 下叫 mcp__loop-exec__run）。它本身不做任何事，只把呼叫連同 run id 轉給引擎的 POST /api/exec/run；引擎依自己的紀錄找出這個 run 的 worktree 掛成 /work，所以 agent 指定不了別的目錄，run 結束後也就不能再用。
  • LOOP_TASK.md 會多一段「GPU 沙盒（執行中可用）」，告訴 agent 寫完就自己編譯、執行、量測，並用 exit code 表達驗證結果。每次執行都會在任務的事件時間軸記一行（指令＋exit code），事後查得到 agent 跑過什麼。
  • Claude 等待 MCP 工具的時間會自動拉長到 exec_max_timeout_sec ＋ 2 分鐘（透過 MCP_TOOL_TIMEOUT），長時間的編譯不會被切斷。

sandbox: 驗證步驟

驗證步驟寫成 sandbox: <指令>，引擎就在同一種容器裡、以 worktree 為 /work 執行它——agent 試過的環境就是引擎驗收的環境。沒有前綴的步驟照舊在主機上跑。沙盒沒開時，這種步驟會直接失敗並說明原因，絕不偷偷改在主機上執行。

# 正確性：程式自己和 CPU 參考值比對，不符就 exit 1
loop add --title "加減乘除 kernel" --goal "…" --plan ./plan.md --repo /path/to/repo --base main \
  --verify "sandbox: nvcc -O3 -o build/arith arith.cu && ./build/arith"

讓驗證可以自動判斷是重點：把「對不對」寫成程式裡的檢查、用 exit code 表達（例如誤差超過容許值就 exit 1）；效能也一樣，用 ncu --csv --metrics … 取出數字，再用一個小腳本檢查門檻。只把輸出印出來、靠人或模型看「看起來對」，不算驗證。注意 --verify 以逗號分隔步驟，指令本身不能含逗號（需要時寫成腳本檔再執行）。

疑難排解

看到原因與處理

項目需求為什麼

    • 驗證通過後，引擎會把結果快轉併進 base 並推上去（auto_merge），晚上一連串任務就能一棒接一棒。
    • main 保持受保護，早上由人看完晨報，再從整合分支開 PR 併進 main。
    • 想讓每個任務都等人按合併，可以 loop config set auto_merge false。注意這是全域設定，所有 repo 都會改成只推分支、開 PR。

評估程式：讓引擎自己判斷過不過

驗收門檻寫在 PRD 的「驗收指標」段，存在任務上，不在 repo 裡。評估程式只負責量，在輸出印一行 LOOP_METRICS 加一個 JSON 物件；引擎拿這些數字比門檻，缺少的指標算不通過。評估程式和標準答案要列進「保護路徑」，被改到就直接判驗證失敗。

# scripts/eval/run.py（範例）
import json, sys
# …逐張跑演算法，和標準答案比對，算出 hit／fp／total…
print('LOOP_METRICS ' + json.dumps({
    'detection_rate': hit / total_defects,
    'false_positive_rate': fp / total_images,
    'miss': total_defects - hit,
    'fps': total_images / elapsed,   # 沒有門檻的指標也會顯示在晨報
}))
sys.exit(0)  # 門檻由引擎比對；程式當掉或讀不到圖才回非 0

可用的比較運算：>= <= > < == !=，也接受 ≥ ≤ =；數字後面的 % 會被忽略。好幾個步驟都有印時，以後面的值為準。不用 PRD 建任務時，可以改用 loop add --metrics "detection_rate >= 0.98; miss == 0" --protect "scripts/eval/**"。

26d操作人員流程：不寫程式也能維護軟體

🧭修問題現在走問題單（第 5b 章）。每個 repo 的「檢查」取代驗證方案，結果頁就是這裡說的驗收頁。下面的工作流程＋驗證方案流程留給評比與進階用途，之後會移除。

分兩種角色：

  • 操作人員：從瀏覽器連進來，說清楚要改什麼、挑驗證方案，早上看結果、自己試跑、確認沒問題再交付。
  • 工程師：事先設定好驗證方案（在哪台機台、跑什麼、用哪些圖資、門檻多少），之後就不用每次參與。

操作人員用到的頁面都在左側導覽：工作流程（開新工作）、晨報、驗證方案；驗收頁從總覽、晨報或對話頁「需要你處理」點任務進去。

  • 最上面的色塊：
    • 綠色：自動驗收通過，指標全部達標，步驟都成功。
    • 黃色：沒有能自動判定的驗證，要靠人工驗收。

  • 結果：
    • 驗收指標表，數字是引擎量的，不是模型自己說的。
    • 每個驗證步驟，點開可以看輸出。
    • 產出物，附大小和 sha256，可以逐一下載。
  • 程式碼：這次改了哪些檔案，可以切換「只看差異」和「完整檔案」。任務的工作區清掉以後照樣看得到，因為是直接從 git 讀。
  • 試跑：
    • 在驗證過的那個版本的獨立副本裡執行，而且只在沙盒裡跑：沒有網路，只看得到這個任務的程式和唯讀圖資。

    • 每次試跑都會記在任務事件裡，包括誰執行了什麼、結果如何。

  • 人工驗收清單：來自驗證方案的人工項目，加上實作者在 VERIFY.md 裡列出的待確認事項。全部勾完才能核可，每一項都記錄誰在什麼時候勾的。

核可之後：下載還是放回 Gitea？

東西放在哪裡說明
原始碼Gitea：loop/<任務> 分支與 PR → 整合分支唯一的正本。核可時，如果合併還在等人，就在這時合併：先把最新的整合分支併進任務分支並重新驗證，通過才合併；沒通過就不核可，並告訴你原因。
產出物（執行檔、報告）引擎主機 ~/.local/share/loop-engineering/artifacts/<任務>/<run>/驗證通過後，從工作區和驗證機台收回來。manifest.json 記錄每個檔案的 sha256，以及機台、commit、指標。這些檔案不會進 git；總大小上限是 artifacts_max_mb。
交付包驗收頁「下載 zip」，或「發佈到 Gitea」
  • zip 裡有：產出物、manifest.json、REPORT.md（驗證結果與指標）、SHA256SUMS。
  • Gitea Release 打在驗證過的那個 commit 上，附同一個 zip，產線從 Gitea 下載。
  • 發佈需要：已核可、有 gitea_url 和 GITEA_TOKEN，而且這個 repo 的 origin 就在那台 Gitea 上。
⚠️在哪種平台建置，就只能在那種平台執行。Spark 建出來的是 ARM64 執行檔，要給產線 x86 機台的版本，驗證方案必須指定規格相同的驗證機台（見第 26c 章）。

工程師：設定驗證方案（只要一次）

在「驗證方案」頁（/plans.html）新增，或用 CLI：

loop verify-plan add --name "亮缺陷判型 — 標準圖集" --repo /srv/repos/cf-aoi --host aoi-gpu \
  --step "cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j" \
  --step "python3 scripts/eval/run.py --gallery {dataset} --golden {dataset}/golden" \
  --dataset-root /datasets --dataset-default 20260615 \
  --metrics "detection_rate >= 0.98; false_positive_rate <= 0.01; miss == 0" \
  --protect "scripts/eval/**" --artifacts "build/cfaoi_ip,reports/*.csv" \
  --check "上機台跑一次選定的圖集，確認判型正確" --domain cuda
loop verify-plan datasets <方案 id>     # 人員會看到的圖資清單
  • 驗證機台：
    • 指定了機台（local 或 loop exec host 登記的名稱），步驟會自動加上 sandbox@…:。
    • 只有在沙盒裡執行的方案，人員才能在網頁上試跑。
    • 沒有指定機台的步驟，會在引擎主機的 shell 直接執行。
  • 圖資：--dataset-root 是容器裡的路徑，它的子資料夾就是人員可以選的圖資，要先用機台的 --data 以唯讀方式掛好。步驟裡的 {dataset} 會換成人員選的那一個。
  • 門檻：評估程式要印一行 LOOP_METRICS {…}，少回報任何一個指標就算不通過（寫法見第 26c 章）。
  • 保護路徑、產出物、人工驗收項目：分別對應「不能動的量尺」「要收回的檔案」「早上要人確認的事」。
  • 檢查機台與圖資：頁面上的這個按鈕，和 loop exec check --host 做同樣的檢查，另外再列一次圖資。
  • 之後修改方案：只影響之後建立的任務。已經建立的任務保留建立當下的方案內容。

確認規則

  • 卡片：準備好的動作會顯示成一張卡片，包含：
    • 引擎寫的摘要（不是模型的轉述）；
    • 三個字的代碼，例如 K7Q；
    • 「確認執行／取消」按鈕。
  • 打字確認：下一則訊息回覆「確認」「好」「OK」這類明確的同意。
    • 高風險動作要附代碼，回覆「確認 K7Q」。高風險包括中止、重來、放棄、刪除、取消評比、核可、合併、git push、git merge。
    • 「好，但改成 sonnet」不算同意，模型會用新的內容重新準備。
    • 模型不能在準備動作的同一則回答裡自己確認，引擎會擋下來。
  • 一次一個：每個對話同時只有一個待確認動作；新的準備會取代舊的。待確認動作 30 分鐘內有效（ops_confirm_ttl_min）。
  • 比較久的動作（送出工作、核可、合併、評分、git）會先回「已開始」，卡片會自動更新結果。也可以問「K7Q 好了嗎？」。
  • 執行前重新檢查：如果任務狀態在準備之後變了，動作不會執行，會請你重新準備。
  • 稽核：每個執行過的動作都會記在任務紀錄，格式是「對話操作（你的名字）：…」。核可也記在你的名字下。
  • 人工驗收清單：對話不會代你勾選，要到驗收頁自己勾。

範本：品質從哪裡來

模型只負責把事實問清楚。PRD、驗證和門檻由引擎用範本組出來，和工作流程頁用的是同一套範本。

工作種類一定會問清楚的事
演算法／誤判（algo）哪一批圖、哪個區域、判成什麼；期望的結果；用哪個驗證方案或圖集。
修 bug（bugfix）怎麼重現，或哪個指令會失敗。
新功能（feature）一個具體的例子。
效能（perf）現況數字；目標數字要有單位（例如 p95 ≤ 300 ms），而且要比現況好；用什麼方式量。
技術評估（spike）要回答的問題；網址必須是你貼過的。
大工作（epic）要拆成的 2–6 塊，以及 repo。

驗證指令只接受四種來源，模型自己想出來的指令會被拒絕：

  1. 驗證方案；
  2. 沿用某張任務的驗證；
  3. 你在對話裡親口說的指令；
  4. repo 偵測到的指令（摘要會標「偵測到，請確認」）。

git

  • 範圍：只能動「可以改的 repo 清單」（prd_repo_allowlist）裡的 repo。新抓的 repo 放在 git_clone_root（預設 ~/Addis/repos），抓完會自動加進清單。
  • 絕不 force、reset、rebase。
  • pull：只快轉。有未提交的修改或分岔時會拒絕，並說明原因。
  • push：摘要會列出要推的 commit。遠端比較新時會拒絕，不會蓋掉遠端。
  • merge：
    • 能快轉就快轉。
    • 不能快轉時，先在暫存的 worktree 做合併 commit；沒有衝突才把分支移過去。
    • 有衝突就放棄合併並列出衝突的檔案；分支和工作區都不會動。
  • clone：只收 https 或 ssh 網址，而且必須是你貼過的網址。網址裡不要放帳號或 token。
  • 和任務錯開：repo 裡有任務正在驗證或合併時，git 動作會等它結束。
  • 引擎自己的 repo（LoopEngineering）預設不能從對話 pull／push／merge，因為會觸發重建與重啟。要開放就設定 ops_git_engine_repo。
