Loop Engineering 完整操作說明

一套用量感知（token-aware）的自主編碼任務排程器 ＋ 協作器。它把編碼任務排入佇列、以必填欄位審核把關，並在你的 Claude 用量低於日/夜門檻時，逐一派給無頭的 Claude Code 在隔離的 git worktree 中執行，跑完你的驗證步驟後停進「待結案」欄，等你收尾。設計為 24/7 常駐 Linux 主機、透過 Tailscale 遠端監看／暫停。

MAX 訂閱 · 以用量百分比排程 單一 Node 程序 ＋ SQLite 看板 · SSE 即時更新 M1–M4 完成

01這是什麼

Loop Engineering 解決一個問題：你想讓 Claude Code 自動、連續地完成一批編碼任務，但又不能燒爆你的訂閱用量。它是一個常駐的「調度大腦」，核心行為是：

  • 排入佇列：把每個編碼任務（目標、計畫、驗證步驟、repo）建成一張卡片。
  • 把關（gate）：必填欄位不齊，任務無法進入排程。
  • 用量感知調度：每 60 秒一個 tick，只有在 session／weekly 用量百分比低於當前時段門檻、且有足夠 runway 時，才派工。
  • 隔離執行：在專屬 git worktree 中跑 Claude Code（無頭、串流 JSON），自動 commit，再跑你的驗證指令。
  • 停進待結案：驗證通過 → review 欄等你人工收尾；失敗 → failed。
ℹ️為什麼用「百分比」而非「金額」？本工具是為固定的 MAX 方案設計，排程依據是用量百分比（session 5 小時窗、weekly 窗），而非美金花費——訂閱制下額度才是限制。

架構一句話

單一 Node 程序 ＋ SQLite（WAL 模式）。沒有 Redis／訊息佇列——用行程內的 60 秒 tick 搭配 mutex 與 max_concurrency。用量透過 TokenBar 的 oauth/usage 契約讀取（session／weekly %），並有 ledger 後備。

02任務生命週期

每張任務卡片會沿著這條狀態機前進：

draft→（審核）→ queued→ running→ verifying→ review→ closed
running 遇到問題 ⤵ blocked（斷路器／硬暫停，額度內 → 自動 resume） attention（timeout／執行錯誤／續跑用盡 → 保留現場，等你決定） failed（使用者中止／放棄 → 終態）
🔀verify 通過後自動收尾（第 13 章）：拉最新 base 併入分支 → 重跑 verify → push 分支 → 自動併回 main 並 push GitHub；遇衝突自動生一個「merge 任務」。所以到 review 時通常已經在 main 上了，你按結案只是最後放行（並放行鏈上的下一個任務）。
狀態意義看板欄位
draft剛建立，尚未通過入場審核Draft · 入場審核
ready審核通過、尚未加入排程Ready
queued已入列，等待調度派工Queued
runningClaude Code 正在 worktree 中執行Running
verifying正在跑你的驗證步驟Verifying
blocked被斷路器或硬暫停中斷，額度內保留 session 自動續跑Queued（可自動 resume）
attention待確認：執行出問題（timeout／執行錯誤／setup 失敗／續跑用盡／最終 verify 失敗），已保留 worktree／session／HANDOFF，卡片顯示失敗原因＋log，等你決定續跑／重來／放棄Review · 結案
review驗證通過（通常已自動併回 main），待你人工結案Review · 結案
failed你中止或放棄的終態Review · 結案
closed你已結案，流程結束（並放行鏈上下一個任務）Closed

06新增任務與入場審核

點頂欄「＋ 新增 task」填寫欄位。入場審核（gate）會逐項檢查；未通過的任務無法加入排程，卡片上會標紅缺項。

欄位必填說明 / 審核規則
Title是任務標題。
Goal是目標描述，不可空白。
Plan是計畫參照：存在的 .md/.html 檔路徑，或合法 URL。
Tool是claude-code／mock（零 token 測試用）／generic（無 git、產出檔案的非編碼任務）／plan（Epic 自主規劃——見下方「任務類型與驗證模式」與第 13 章）／deploy（部署任務，不派工給 agent——見第 19 章）。
Verify steps是*至少一條驗證指令（逗號分隔），例：npm run lint, npm test。verify mode 含 manual／llm 或 tool=plan／deploy 時可免
Repo path是*存在的 git repo 目錄。mock／generic 略過
Base branch是*存在的基底分支。mock／generic 略過
Complexity—S/M/L（預設 M）；決定逾時與預估用量。
Priority—整數，預設 2。
Model—留空＝用全域預設模型（default_model，預設 sonnet = Sonnet 5）。要對單一任務加碼可選 opus／haiku／fable-5。
Setup cmd—派工前在 worktree 執行的準備指令（如 npm ci）。未填只是警告。
Environment—（deploy 必填）套用對應 env:<name> 知識；tool=deploy 時同時是部署目標，必須是已存在的 environment（見第 19 章）。

* Repo/branch 僅在工具為 claude-code／deploy 時必填；mock／generic／plan 不在 git repo 中執行，故略過 repo 檢查。Verify steps 僅在 verify mode 不含 manual／llm 且 tool 不是 plan／deploy 時必填。

任務類型與驗證模式

Tool 決定任務在哪裡、怎麼跑；Verify mode 決定怎麼判定完成。兩者互相獨立，可自由組合（例：generic ＋ llm 用來跑一份分析報告，由 LLM 對照 rubric 判斷是否合格）。

Tool執行位置Git 收尾用途
claude-code專屬 git worktree（loop/<id> 分支，從 base 切出）完整（見第 13 章）：commit → push → 併回 base → PR一般編碼任務。
mock暫存目錄（每次 run 全新建立，用完即棄）無（零 token 測試/演練用，不代表真實產出）排程器/斷路器/watchdog 的零 token 測試。
generic持久化產出目錄 ~/.local/share/loop-engineering/outputs/<id>（跨 resume 保留，結案也不會被清掉）完全略過——不建 worktree、不 commit、不 push、不併回、不開 PR非編碼工作：報告、資料分析、一次性腳本、設計產出等。真的呼叫 Claude Code（非 mock），只是不碰 git。
plan（Epic）不執行任何工作區——AI 規劃器把目標拆成子任務，子任務才各自建 worktree無（本身不改任何程式碼；子任務照常走完整收尾）一句話丟一個大目標，自動拆成 2–6 個子任務並依序自主執行——見第 13 章「Epic 自主規劃」。
deploy不派工給 agent——直接在 repo_path 執行 deploy_cmd（環境 auto_deploy=1），或產出 outputs/deploy-<id>/DEPLOY.md 部署包（auto_deploy=0）無（不是編碼任務，沒有 diff 可併）把 environment 從知識標籤升級成真正的部署目標——見第 19 章「環境與部署」。
📄generic 的產出怎麼看？看板卡片顯示「📄 產出 N」徽章；點開卡片可看產出目錄路徑與檔案清單（名稱＋大小，最多列 ~50 個）；也可呼叫 GET /api/tasks/:id/result 或 MCP 的 loop_task_result 取得同樣資訊。
Verify mode怎麼判定完成備註
command（預設）執行 Verify steps，全部 exit 0 才算過。至少要有一條指令；generic 的指令在產出目錄執行。
llm把變更（claude-code／mock 是 git diff；generic 是產出目錄的檔案清單＋小型文字檔摘錄）連同 Rubric 交給 LLM 判官，回覆 pass/fail。需填「驗收標準 Rubric」；判官不可用（無 claude CLI／用量已達硬上限）時絕不自動放行，改判為 manual。
manual一律停在待人工驗證，由你依 Rubric／產出親自確認後按合併或結案。可免填 Verify steps；claude-code 會請 agent 寫一份 VERIFY.md 交接手動驗證清單。

Verify mode 可複選（逗號分隔，如 command,llm）：只要其中一種判定失敗，就整體算失敗；只要包含 manual，最終一定停在待人工驗證。

07CLI 指令參考

在主機 repo 目錄執行。兩種呼叫方式：開發用 npm run loop -- <cmd>，或用建置產物 node dist/cli.js <cmd>。

指令作用
add建立任務（起始 draft）。旗標：--title* --goal* --plan --tool --verify --setup --repo --base --complexity --priority --model --depends-on <taskId>（串行鏈：押住直到該任務結案）
gate <id>顯示該任務的入場檢查清單。
chat prune [--days n] [--yes]刪除超過保留天數的對話（含圖片檔）。不加 --yes 只列出要刪什麼。
chat export <id>把一段對話輸出成 Markdown 到 stdout（--reasoning 連思考過程一起）。
queue <id>審核並把 draft 加入排程。
list [--status <s>]列出任務（可依狀態過濾）與各狀態計數。
status顯示排程暫停狀態、session/weekly 用量、各狀態計數、進行中的 run。
pause [--hard]暫停排程。--hard 會一併中斷執行中的 run（轉 blocked，可 resume）。
resume恢復排程。
abort <id>中斷該任務的 run 並標記 failed。
close <id>把已審閱的任務標記 closed（並放行鏈上下一個任務）。
delete <id> [--force]永久刪除任務＋磁碟產物（worktree／plan／logs）。
prune [--status <list>] [--older-than <days>] [--yes]批次清理終態任務＋產物（預設 dry-run，加 --yes 才真刪）。
config [list｜get｜set] [key] [value]檢視 / 即時修改排程設定（門檻、模型、Git 收尾旗標）。例：loop config set default_model sonnet。改完下一個 tick 生效、免重啟；含防呆。
set-usage --session <%> [--weekly <%>]開發用：強制寫入共享用量快取（斷路器演練）。
forecastBacklog 用量預估（見第 17 章）；若有可比較資料，尾端再附一行執行紀律 A/B 摘要（見第 18 章）。

09三層預算保護

為避免燒爆用量，派工到執行有三道獨立防線：

① 派工前 gate

tick 時先看用量快照：若 session/weekly 已達當前時段門檻，或 runway 不足 min_runway_min，就不派工。

② 執行中斷路器

執行期間若用量衝破 hard_limit_pct（95%），立即中斷該 run（SIGINT → SIGKILL），任務轉 blocked（保留 session，用量降回後自動 resume）。

③ 每run watchdog

每個 run 有依複雜度而定的逾時（S/M/L = 15/45/120 分）；逾時即殺並標 failed。

🛡️另有內層保險：PreToolUse 的 budget-guard.mjs hook 會在硬上限阻止工具使用——即使排程層失守，被派出的 Claude 也會被擋下。

13自動化：Git 收尾與任務鏈

這一章講三件讓 Loop Engineering 能自己一路做下去的機制，以及人與引擎的分工。

1 · running 的標準流程（Git 自動收尾）

每個 claude-code 任務跑完後，引擎自動走這條收尾（全部可用第 8 章的旗標關閉）：

  1. 派工時從 fetch 過的最新 origin/<base> 切 loop/<id> 分支（不再從過期本地 main）。
  2. Claude Code 修改 → 自動 commit → 跑你的 verify 步驟。
  3. 把最新 base 併進分支；若有變動重跑一次 verify。
  4. push 分支備份 → FF-only 自動併回 main 並 push 到 GitHub。
  5. 卡片進 review，徽章顯示 ✓ 已合併。
🛡️安全保證：所有網路 git 操作都有 30 秒逾時、失敗不會卡住引擎；併回一律 fast-forward-only，絕不改動你的髒工作區、絕不強推。無法乾淨 FF（例如你的 base 有未推的本地 commit）就降級為 待合併，卡片上按合併再試。
🧩遇衝突自動解：併回若衝突，引擎自動建一個 merge 任務（標題 [merge] …），交給 Claude Code 拉最新 base、解衝突、跑 verify，再自己走一次收尾。你不用手動處理。

2 · attention（待確認）：出問題時保留現場交回人工

過去出問題只有「自動續跑」或「直接 failed」兩種。現在多了一個待確認狀態：watchdog 逾時、執行錯誤、setup 失敗、續跑用盡、最終 verify 失敗，都會落到 attention（顯示在 Review 欄），保留 worktree／session／HANDOFF，卡片列出失敗原因與 log。你有三個動作：

動作作用
續跑沿用原 session 與 HANDOFF，從中斷處接續（給一次額度）。
重來清掉 worktree 與 loop/<id> 分支、歸零續跑計數，從最新 base 重新開始。
放棄標記 failed 終態（可選一併清 worktree）。
🧷使用者「中止」是終態：按中止（或 abort）的任務直接 failed、不會偷偷自動復跑。想暫停但保留可續跑，用硬暫停（pause --hard）→ 轉 blocked。

3 · 任務鏈（depends_on）：嚴格 A → B → C

要讓任務一個做完才做下一個（例如彼此會改到同一批檔、或後者依賴前者的成果），用依賴鏈，避免多個任務同時從舊 base 切分支互相衝突：

# CLI：B 依賴 A
npm run loop -- add --title "B" --goal "…" --plan ./B.md \
  --repo /path --base main --verify "npm test" --depends-on <A的id>
  • 帶 depends_on 的任務會被押住不派工，卡片顯示 ⏳ 等 t_xxx。
  • 前置任務結案的那一刻，引擎自動放行下一棒（dep_auto_queue）。
  • 前置若 failed 或被刪除，後者押住等你處理，絕不誤跑。
  • MCP 也支援：建 B 時說「依賴 A」。

4 · Epic 自主規劃（coding_tool=plan）

ADO＋Copilot 仍需要人把 Epic 拆成 Feature／Story 才能派工；Loop 的差異化能力是：只丟一個大目標，AI 規劃器自動拆成一條 depends_on 子任務鏈並自主執行到底——就是你原本手動拆任務鏈的動作，改由 Loop 自己做。

  1. 建一個 tool=plan 任務（Title/Goal 照填；Plan 欄位當作「Epic 說明書」，可以寫得比一般任務詳細）。Repo／Base／Model／Environment 這幾欄若填了，會被子任務繼承；不填也可以（純規劃）。
  2. 派工時不會建立 worktree，而是呼叫規劃模型（default_model，通常比知識蒸餾用的 haiku 更強），把「目標＋Plan＋相關知識」丟給它，要求輸出 2–6 個子任務（含各自的 goal／verify steps／複雜度，彼此若有先後用 order 表示）的嚴格 JSON。
  3. 規劃結果materialize 成一串真正的 claude-code 子任務：parent_id 指回這個 Epic、依 order 用 depends_on 串成鏈、繼承 Epic 的 repo/base/environment/model。第一個子任務（若通過 gate）直接 queued，其餘留 draft，交給既有的任務鏈機制（見上方第 3 節）依序放行。
  4. Epic 本身立刻結案（closed，卡片顯示「已拆解為 N 個子任務」）——它的工作就是產生子任務鏈，之後全程由子任務照常跑收尾／verify／人工核可。
  5. 規劃失敗（模型沒回應、輸出解析不出來、用量已達硬上限）Epic 轉 attention，可續跑重試或改手動拆任務。
🧬看板怎麼看：Epic 卡片顯示「子任務 n/m 完成」rollup 徽章；子任務卡片顯示「↳ epic: t_xxx」回指徽章；點開任一張卡片的詳情視窗都能看到完整的子任務清單與各自狀態。
⚠️Epic 任務不需要（也不會用到）Verify steps／Repo／Base——這些檢查全部略過；真正需要驗證的是它產生出來的子任務。
📐SDD 規格模式（sdd_specs，預設關）：預設每個子任務都共用同一份 Epic 說明書當 plan_ref。開啟 sdd_specs 後，規劃器改為每個子任務生成一份自足規格 spec-*.md（背景／驗收情境／限制／out-of-scope）當各自的 plan_ref——讓沒有其他背景的實作者（或便宜模型）只讀那份規格就能可靠完成。這正是把「便宜模型」下放到實作階段（model_routing，見第 8 章）的前提。關閉＝規劃器提示與子任務 plan_ref 與改版前完全一樣（零影響）。

知識圖譜視覺化（Obsidian 式 [[wikilink]] ＋ 多跳 ＋ force-directed）

在節點 body（或 ~/SSoT vault 裡的 markdown 檔）寫 [[標題]] 就會自動建關聯：節點對節點的 wikilink 直接變成一條 links-to 關聯（跟手動建的關聯一起顯示、可刪，但只要 body 裡還留著該 [[wikilink]]，下次存檔就會自動重建）；vault 裡的 markdown 檔本身會成為圖上的文件節點（方形，跟節點的圓形區分），連到它連結的節點或其他文件——這一段解析在每次 loop ingest run 之後全庫重跑一次，所以連結目標晚於連結本身被 ingest／新增也會在下一次自動接上。

  • 開啟方式：知識庫頁頂欄「🕸 圖譜」看整張圖；某節點列的「關聯」鈕則以該節點為中心開一張多跳鄰居圖（右上角「展開跳數」可調 1–6 跳）。
  • 操作：拖曳空白處平移、滾輪縮放、拖曳節點喬位置、點一下節點（不拖曳）會即時向伺服器多要一跳鄰居併入目前的圖（既有節點位置不會被打斷）。
  • 篩選：面板內有 kind 篩選、來源篩選（節點的 source／文件所屬的 ingest 來源）、標籤與 scope 關鍵字過濾，以及「顯示文件節點」開關（關掉只看策展知識，不看語料文件）。
  • 純 vanilla 實作：整張圖是手刻 canvas 2D force-directed（web/graph-layout.js 純運算＋web/brain.js 畫面／互動），沒有外部圖表庫、沒有 CDN，符合看板一貫的 textContent-only（canvas 文字是像素，本來就不是 HTML，不會有注入風險）。

知識圖譜關聯（auto-relate）：自動推斷節點間的關係

手動建關聯很容易越積越少——這功能用混合策略幫知識庫補關聯，同樣草稿制、永不自動核准：先用既有的向量索引（vec_nodes，sqlite-vec，cosine 距離）取每個節點嵌入空間裡最近的 5 個鄰居當候選配對（避免 N² 全配對），再用一次 haiku 呼叫幫候選配對判斷關係型別（runs-on／constrains／deployed-at／uses／part-of／related）並濾掉沒有實質關聯的配對——輸出的邊一律以草稿關聯入庫，跟既有邊（同來源、去向、關係型別）重複的一律略過，不會產生重複邊。

  • 怎麼觸發：知識庫頁頂欄「🔗 推斷關聯」鈕；或 CLI loop knowledge relate [--limit N]（--limit 控制單次最多評估幾組候選配對，離越近的配對優先，預設 20）；或 API POST /api/knowledge/relate。
  • 怎麼審核：知識庫頁「草稿關聯」區塊列出所有待審核的建議邊（來源／關係／去向＋理由），逐條「核可」或「退回」——核可後才會出現在圖譜與任務注入裡；退回不會刪除紀錄，只是不再視為待審。
  • 絕不自動生效：草稿關聯在核可前不會出現在「🕸 圖譜」畫面，也不會被派工時的知識注入（knowledgeContext）當成一跳關聯使用——跟草稿節點的審核邏輯完全對稱。
  • 零 token 前提：沒裝 claude CLI，或本節 session 用量已達 hard_limit_pct，都不會呼叫 LLM（也不會消耗嵌入運算）；沒有觸發前，圖譜與任務注入行為完全不變。

15SSoT／RAG／擷取管線

第 14 章的知識庫是策展層——小量、人工核可、會注入任務 prompt。這一章是它的擴充：一個語料層（documents／chunks），把整個 codebase、筆記 vault 甚至 GitHub issues 都受治理地擷取進同一個 loop.sqlite，支援混合語意檢索（RAG）與可追溯的引用——但只在被查詢時才選擇性拉出，絕不整段塞進任務 prompt（維持第 14 章「零影響」的策展層不變）。

🗂️兩個資料平面。策展圖譜層（knowledge_nodes/edges，第 14 章）＝小量、人工核可、注入 prompt；語料層（documents/chunks，這一章）＝大量原始擷取內容，只供 RAG 檢索、選擇性拉 top-K。兩層以 doc_links／node_chunk_links 連結（例如 vault 筆記的 [[wikilink]]、或蒸餾草稿的語料佐證）。

來源登錄與擷取管線

先登錄一個來源（sources 表），再觸發擷取：

# 登錄：git repo（受 .gitignore、只取已追蹤檔）／folder／Obsidian 風格 vault
loop ingest add --git ~/Coding/LoopEngineering
loop ingest add --vault ~/SSoT
loop ingest list
loop ingest rm <source_id>

# 擷取：全部已啟用來源，或指定一個
loop ingest run
loop ingest run <source_id>
  • 受治理 walker：git 來源用 git ls-files（尊重 .gitignore）；folder/vault 用遞迴 walk。一律排除 node_modules/dist/.git、二進位、鎖檔；.env*／.pem／id_rsa 等金鑰檔名整檔跳過；檔案大小超過 ingest_max_file_kb 也跳過。就算檔案通過了這層，內文裡看起來像私鑰區塊／AWS／OpenAI／GitHub／Slack token／key="..." 這類樣式，也會被逐一遮蔽成 [REDACTED] 才進索引。
  • chunker：markdown 依標題切塊、程式碼依函式/行窗切塊，每個片段都記 start_line/end_line 供之後的引用；每個片段被嵌入／建 FTS 索引的文字都會前綴該文件的 title，確保只存在標題裡的關鍵詞（例如專有名詞、work package 主旨）也能被向量與關鍵字檢索到。
  • 增量、bi-temporal：以檔案內容 sha256 比對——沒變的檔案整個略過（skipped_unchanged），變了的檔案舊版標記 invalid_at（保留歷史，不刪除）並產生新版文件／片段；來源裡消失的檔案同樣被標記失效，而不是砍掉重練。
  • 觸發方式：CLI loop ingest run [source]、MCP loop_ingest／loop_sources、REST POST /api/ingest／GET /api/sources。

OpenProject 來源

第五種來源類型：把 OpenProject 伺服器裡的 work packages（含主旨＋描述）與 projects 擷取進 SSoT，之後能用中文語義跟程式碼一起檢索。不重新實作 OpenProject client——重用使用者既有的 ~/Coding/OpenProject_Exec_Report/op_api.py（零外部相依、Python 3.8 相容，已封裝認證／分頁／自訂欄位／normalize）。

loop ingest add --openproject ~/Coding/OpenProject_Exec_Report
loop ingest run <source_id>
  • 運作方式：Node 端注入式 spawn scripts/openproject_dump.py（僅 stdlib）——把 --openproject 的 repo 路徑加進 sys.path 後 import op_api，呼叫其 get_work_packages／get_projects；每筆輸出一行 JSON，Node 端逐行解析後走既有的 chunk→embed→store 管線；壞掉的單一行只會被跳過，不會讓整次擷取失敗。
  • 增量規則跟檔案型來源不同：檔案型來源用內容 sha256；OpenProject 用該筆項目的 updatedAt（無此欄位才退回 sha256）——伺服器端已修改的 work package 才會被重新擷取，沒改的整批略過。
  • 登錄時做的事：loop ingest add --openproject <repo> 會讀該 repo 的 config.json（預設路徑，--op-config 可覆寫）取出 op_base_url 當作來源的 uri（供之後 loop_search 的 scope 過濾用）——只取這一個欄位，op_api_key 全程不讀取、不複製、不寫入 log，僅由 op_api.py 自己在 spawn 出的 python 行程裡本機讀取使用。
  • 只取兩種項目（wiki／工時暫不做）：--kinds work_packages,projects（預設兩者都取）；每份 work package 文件的可檢索文字＝主旨＋描述＋少數有意義分類欄位（類型／狀態／負責人／專案），活動留言的時間戳雜訊不收錄（title 仍另存 #<id> <主旨> 不變）；引用連結（document.uri）指到 <op_base_url>/work_packages/<id>；project 文件指到 <op_base_url>/projects/<identifier>。
  • 沒登錄 openproject 來源＝零行為變化；沒設定 ingest_openproject_python 時預設呼叫 python3（公司 Windows 部署若執行檔叫 python，改這個設定即可，不需要改程式碼）。

混合 RAG 檢索

語料層可用混合檢索查：FTS5 trigram 全文（跟第 14 章知識庫搜尋同一套中文友善索引）⊕ 向量 KNN 語意搜尋，兩路排名以 RRF（Reciprocal Rank Fusion）融合，回傳帶引用（來源路徑／行號／分數）的片段。

  • 本機 GPU 嵌入：rag_enabled=false（預設）時完全不會嵌入、不會載入模型——自動退回純 FTS 全文檢索，一樣可用，只是少了語意召回。開啟後用 embed_model（預設 BAAI/bge-m3，1024 維、多語含中文）透過 voice-venv 的常駐 worker 嵌入，同一顆 GPU 與語音 whisper worker 共用、互斥、閒置自動釋放 VRAM（embed_worker_idle_min）。
  • sqlite-vec：向量存在 vec_chunks／vec_nodes 兩個 vec0 虛擬表；loadExtension 失敗（例如平台沒有對應的 .so）會安靜降級為 FTS-only，不會讓伺服器起不來。
  • 怎麼查：MCP loop_search（回帶引用的片段，適合問「這段邏輯在哪裡」）、REST GET /api/rag/search?q=...。
  • 任務內自動帶語料（旗標，預設關）：rag_inject_task_context=true 時，派工除了第 14 章的策展知識，還會額外拉該 repo scope 的 top-K 語料片段，附進 LOOP_TASK.md 一個獨立的「相關語料 (RAG)」段（有 char 預算上限）；關閉＝完全不影響 prompt。

快速記錄（capture）：一句話寫進 SSoT vault

不想手動開 Obsidian 建檔時，用擷取：寫一則 markdown 筆記進已登錄的 SSoT vault，並立即索引，馬上就能被 loop_search 搜到。跟第 14 章「＋ 新增」的策展知識節點是完全分開的兩層——擷取寫進語料層（documents/chunks），不會注入任何任務 prompt；要留一條「以後每個任務都要遵守」的長期事實，還是用 loop_remember／知識庫頁的「＋ 新增」。

  • MCP：loop_capture（text 必填，title 留白則取內文第一句，tags 選填）。
  • 看板：知識庫頁（/brain.html）頂欄「📥 擷取」開一個輕量對話框，寫完按「寫入」，成功後顯示新增了幾份文件／幾個片段。
  • REST：POST /api/capture（{"body":"...","title":"...","tags":[...]}）。
  • 寫入的目的地是第一個已啟用的 kind=vault 來源——先用 loop ingest add --vault ~/SSoT 登錄一個，擷取才有地方寫；沒登錄會回 400 錯誤說明原因。

17Backlog 用量預估

回答「還能不能再加任務？」：把既有的每任務估計（est_pct_* / est_weekly_pct_*）加總成一個 backlog 預測，純讀取、不影響排程或預算行為。「pending」= 非終態任務（draft/ready/queued/running/verifying/blocked，排除 closed/failed/review/attention）。

  • Weekly 是累加約束（整週不會中途歸零）：weekly_backlog_pct = 所有 pending 任務的 estimateWeeklyPct 加總；weekly_headroom = max(0, weekly_max − weekly_now − weekly_backlog_pct)。
  • Session 是逐窗口的（每 5 小時歸零一次）：不把 backlog 的 session 估計加總，只回報其中最大的單一任務估計（largest_task_session_pct）與是否塞得進一個 session 窗口（largest_task_session_fits，即 ≤ hard_limit_pct − safety_reserve_pct）。
  • verdict：依 weekly_headroom／capacity_more_M 分四級——plenty（餘裕多）／some（還加得下幾個）／tight（勉強擠得下）／full（額度已滿）。

四個入口都看得到同一份預估：看板頂欄 chip（見第 5 章）、loop forecast CLI（見第 7 章）、GET /api/forecast（見附錄）、以及 MCP 的 loop_status（見第 12 章）——問「Loop 還能加幾個任務？」它就會回。

📐只讀既有估計，不新增任何調度判斷——關掉這個功能（不呼叫它）對排程/預算行為零影響。

18執行紀律（實驗性，預設關）

社群傳的「Superpowers 6.0 = 速度 2 倍／token −50%」是誤讀了 Superpowers 自己 6.0 對比 5.x 的 changelog（不是對比原生 Claude Code）；獨立測試顯示平均省 ~14%、簡單任務反而更貴，而且它的工作流程本來就偏吃 token。把整個 plugin 裝進 Loop 是淨負面：Loop 無頭派工的 --allowed-tools 沒有 Skill/Task，它的技能大多根本不會被觸發（描述注入的 token 白花）；brainstorming 技能會反問使用者，對無人值守是致命的；worktree／plan／code-review／subagent 相關技能還會跟 Loop 自己的 worktree.ts／planner／gapReviewer／verify 重複＋衝突。

所以：不安裝 plugin。唯一真正可搬、不衝突、便宜的部分，是三個「純提示詞」紀律：test-driven-development、systematic-debugging、verification-before-completion。這裡把它們濃縮成一段選配的 ## 執行紀律 提示（見 src/orchestrator/prompt.ts），完全不含 subagent、不含反問，由 prompt_discipline 開關控制（預設 false ＝ 對 LOOP_TASK.md 零影響）。

  • 怎麼開：看板 ⚙ 面板「執行紀律（實驗性）」，或 loop config set prompt_discipline true。
  • 怎麼量測：開/關各跑幾個可比較的任務，用 GET /api/metrics 看「執行紀律 A/B」資料——依每個結案任務最新一次 run 的 discipline 分組，列任務數、平均實際 session %／任務（session_pct_before/after 差值加總）、待確認率、平均續跑次數、平均週期。同一份資料也能從 GET /api/metrics 或 loop forecast CLI 尾端看到。
  • 誠實原則：這是量測工具，不是背書——效果好壞看你自己的任務跑出來的數字，不是相信這段文案。
💡Superpowers 這個 plugin 本身很適合互動式 Claude（brainstorming 等技能靠使用者來回才有價值），只是不適合 Loop 這種無頭排程執行——兩者的使用情境不同，不是互斥。

SDD × 便宜模型 A/B（同一套量測骨架）

核心假設：把規格寫到夠精準，便宜模型（haiku）就能達到強模型面對模糊目標的水準，且更省額度、rework 更少。「更好」＝同一個 5h/週額度窗口出更多貨、變異更小。這是要用資料驗證的假設，不是可直接假定成立——所以先量測再開分流。

  • 怎麼標記：新增任務時用 loop add --experiment <名>（或 MCP loop_add_task 的 experiment 參數）。這是純標籤，完全不影響排程／入場審核。
  • 怎麼比：挑幾個代表性目標，各建兩次——A＝模糊目標＋sonnet＋--experiment ab_A；B＝手寫 SDD 規格 .md 當 plan_ref＋--model haiku＋--experiment ab_B；在拋棄式 repo/branch 序列跑（勿並行同檔任務）。跑完 loop experiment ab 看兩組的 pass 率／平均 session%／attention 率／resume。
  • 放行閘門：唯有 B 組（SDD＋haiku）在 pass 率不劣、且額度顯著更省時，才把 model_routing 開起來、route_S 調成 haiku（見第 8 章）。這也是為什麼分流預設全關。
  • Epic 版：開 sdd_specs 後，tool=plan 的 Epic 規劃器會自動為每個子任務生成獨立自足規格（見第 13 章），就不必手寫 B 組規格。

19環境與部署（Environments + Deploy）

environment 欄位原本只是套用 env:<name> 知識的標籤；現在額外對到一張真正的 environments 表，把「環境」升級成一個可執行的部署目標——服務「在家開發、帶去公司部署」：home 設 auto_deploy，本機直接跑 deploy_cmd；company 不設 deploy_cmd（auto_deploy=0），改產出一份部署包＋人工檢查清單，帶去公司照做。

部署任務怎麼跑（tool=deploy）

  • 不派工給 agent、不建 worktree、不跑驗證——直接解析 environment／repo_path／base_branch，記下要部署的 commit（base_branch 的 git rev-parse）。
  • auto_deploy 環境（如 home）：在 repo_path 執行 deploy_cmd；exit 0 → deployments 記一筆 deployed（含 commit），任務轉 review；非 0 → 記 failed，任務轉待確認。
  • manual 環境（如 company，auto_deploy=0）：不執行任何指令，改在 outputs/deploy-<id>/DEPLOY.md 寫一份部署包（commit、repo/base、依知識庫 env:<name> 整理的環境限制、人工部署步驟），deployments 記 manual-pending，任務轉 review「待人工部署」——帶去公司照著做，做完回來按結案。

回滾

loop deploy rollback <env> 或 POST /api/deployments/:id/rollback：找出該環境上一筆 deployed 的 commit，新增一筆 rolledback 記錄指向它；auto_deploy 環境會帶 LOOP_DEPLOY_SHA 環境變數重跑 deploy_cmd（by design 不直接動你的 checkout——要 checkout 到該 commit 由 deploy_cmd 腳本自己用這個變數處理，符合「絕不動使用者 checkout」的鐵律）；manual 環境則產出 outputs/rollback-<env>-<id>/ROLLBACK.md 人工檢查清單。

☁看板卡片上會看到「☁ deploy: company (manual-pending)」這類徽章；點開卡片可看部署環境／狀態／詳情（含 DEPLOY.md 路徑）。新增任務對話框的 Environment 欄位下拉，同時合併知識庫 env:<name> 與這張 environments 表的名稱。

20交付 pipeline 模板（CLI／API）

🗑️/pipelines.html 已於 2026-09 移除；/api/pipelines、loop pipeline 與看板上的 pipeline 進度條都還在。

ADO 的 multi-stage pipeline 是人工寫的 YAML（build→test→deploy）、推 push 觸發；Loop 的自主版是預定義模板——一個動作就把「implement → verify → deploy」這種固定分解，實體化成一條第 13 章的 depends_on 任務鏈，每個 stage 沿用既有的驗證模式（command／llm／manual，見第 6 章）與第 19 章的部署當作自己的關卡。這不是新的執行語意，只是 depends_on + verify + deploy 的一個方便組合。

  • 模板存哪：pipelines 表（name 主鍵、def JSON），首次啟動即從 seed/pipelines/*.json 播種（INSERT OR IGNORE，不覆蓋你自己的修改，作法同第 19 章的 environments 播種）。內建三個：feature（implement → llm-gate → deploy home）、fix（implement → command-verify）、ship（implement → verify → deploy home → deploy company〔人工〕）。
  • 怎麼跑：loop pipeline run <name> --goal "…" --repo /path --base main [--env home] [--title "…"] [--verify "npm run typecheck,npm test"]，或 POST /api/pipelines/:name/run，或 MCP 的 loop_run_pipeline。goal／repo／base／verify 由每個 stage 共用（因為改的是同一份 code），各 stage 自己的 verify_mode／environment／complexity 則照模板固定。
  • 實體化：依模板順序建出一串任務，用 depends_on 串成鏈，共享一個新的 pipeline_id（+ 各自的 stage_name，如 implement／deploy-home）；第一個 stage 通過 gate 就直接 queued，其餘留 draft，交給第 13 章既有的任務鏈機制依序放行。
  • 關卡＝既有驗證模式：command stage 要跑過驗證指令；llm stage 要過 rubric（模板的 rubric_hint 會變成該任務的 verify_rubric）；deploy stage 走第 19 章的部署（環境是 auto_deploy 就自動部署，否則產出人工部署包）。任一 stage 失敗（failed）就停在原地——下一棒的 depends_on 判定為 dep-failed，永遠不會被自動派工，跟第 13 章第 3 節的任務鏈規則完全一樣，沒有另外發明失敗處理。
  • 看板：頂欄下方多一條 pipeline 進度列，例如「feature: implement ✓ → review-gate ⏳ → deploy-home ○」，點任一 stage 開該任務詳情；卡片本身也會多一顆「🚦 stage 名稱」徽章，詳情視窗列出整條 pipeline 各 stage 的狀態。
  • 自訂模板：loop pipeline list 看目前有哪些；loop pipeline import [file]（不給檔案就重新匯入內建 seed/pipelines/*.json）或 POST /api/pipelines/import 批次匯入——壞掉的 stage（缺 name、coding_tool 不合法等）該筆會被拒絕並回報原因，不影響其他筆匯入成功。
# CLI：用 ship 模板一次交付到兩個環境
npm run loop -- pipeline run ship \
  --goal "上線第三方登入" --repo /path --base main \
  --verify "npm run typecheck,npm test"
🚦Pipeline 只是幫你一次生出一條固定的任務鏈；生出來之後，續跑／重來／放棄／attention 觸發，全部跟一般任務鏈一模一樣（見第 13 章）——沒有專屬的例外處理。

21ADO/GitHub 整合橋接

D5：Loop 不取代公司的 ADO/GitHub，而是插在它上面當自主執行層——從 ADO/GitHub 拉一張 work item/issue → 建成 Loop 任務 → Loop 自主實作 → 把結果（PR 連結＋狀態）推回原 work item 留言。預設整個功能全關、零外部呼叫；只有明確設定 provider 並在環境檔案填妥憑證後才會動作。

  • 啟用：loop config set integration_provider github（或 ado；預設 none＝完全關閉，不論憑證是否存在都不會呼叫外部）。憑證只放在 ~/.config/loop-engineering/env（絕不進 SQLite、絕不進 log）：GitHub 用 GITHUB_TOKEN（＋選填 GITHUB_API_URL，支援 GHES）；ADO 用 ADO_PAT / ADO_ORG / ADO_PROJECT（三者缺一即視為未設定）。
  • 拉取（import）：loop pull --provider github --query "assignee:@me label:loop repo:owner/name"（GitHub 的 query 是 search 語法；ADO 則整段當 WIQL 查詢），或 POST /api/integrations/import，或 MCP 的 loop_pull_workitems。每個 work item 建一個 Loop 任務（標題/目標取自 item、plan 由內容合成），並記一個新的 source_ref 欄位（如 github:owner/name#123 / ado:456）——同一個 query 重跑不會重複建立（依 source_ref 判斷已存在即跳過）。建立後依 max_autoqueue 剩餘額度自動入列，其餘留 draft。
  • 推回（pushback）：任務進到 review／closed 時，若該任務有 source_ref 且 integration_pushback 設定為 true（預設 false），背景（fire-and-forget，不擋 tick）在原 work item 留言 PR 連結＋狀態；失敗只記一筆 note，不影響任務本身。
  • 看板：卡片上會看到「⇄ github#123」這類徽章（從 source_ref 解析）；點開卡片可看完整來源與最近一次 pushback 結果。
  • 測試：src/__tests__/integration.test.ts——provider 的 fetch 全部注入假實作，零網路；涵蓋 listWorkItems 解析/失敗降級為 []、import 的建立與冪等、pushResult 的留言內容、pushback pump 的旗標/憑證閘門。

24報告圖表（Mermaid）與存檔

使用者回饋報告純文字太多——這一版把甘特圖／狀態圓餅圖（可選相位流程圖）加進報告，並可選擇把報告連同原始資料、圖表存到本機目錄，讓你直接抓圖貼簡報，或用自己的 git 追蹤歷史。圖表資料一律由 src/report/charts.ts 的純函式從結構化 work package 資料程式化產生，LLM 完全不碰數字——LLM 只負責寫「摘要 / 風險與落後 / 下一步」的敘述文字，不再重述甘特圖已經呈現的逐筆進度/交期表格。存檔功能預設關閉（report_persist=false），零行為影響。

25企業週報 PPTX（公版格式）

公司要的不是「AI 排版的簡報」，是「填進公版格式、人眼一眼認得出來的週報」——所以這條線徹底反過來做：LLM 只產出結構化 DeckSpec JSON（status 文字／說明頁敘述），版面本身一律由 scripts/report_pptx.py 對公版模板做確定性 fill-only 渲染，絕不在執行期生成版面、複製投影片或調整位置。四條任務鏈（T1 模板+渲染器、T2 週組裝+人工把關、T3 LLM status+品質閘門、T4 這裡：一鍵命令＋REST＋MCP＋本文件）都已合併進 main。預設整個功能關閉（report_pptx_enabled=false），零行為影響——沒開之前，loop report pptx/weekly * 直接印提示 fail-fast，POST/GET /api/report/weekly* 一律回 404，MCP 的 loop_report_weekly 呼叫會失敗並附帶錯誤訊息。

功能總覽

  • 公版 fill-only 渲染：模板製作期把公版原型頁複製成固定容量的 pool（1 頁總表＋N 頁主頁＋N×2 頁說明頁，見下方「模板製作」），渲染器只認 shape 名字（LOOP: 慣例）把值填進去或清空，絕不在渲染時期新增/刪除投影片或改版面座標。
  • 黑／藍／紅確定性上色規則：每個 status 項目跟上週實際出貨的 deck-spec.json 做純函式 diff（src/report/pptx/diff.ts）——文字完全相同＝black（沿用中）；新出現的文字＝blue（新增）；人工手動標記的＝red（需高層關注，一旦手動標紅就不會被自動重新分類覆蓋）。這條規則在 render／run 階段每次都會重新計算，所以就算你手改了 status 文字，顏色仍會正確反映「這段文字跟上週比是不是新的」。
  • 品質閘門（Skywork 對標）：LLM 生成 status 候選後，先跑一次 haiku 潤稿（文法/贅字/壓成單行），再用 llm_judge_model 依「綜合評分／有無引用進度佐證（work package 來源）／潤稿完成度」評分；沒過就帶著 judge 的 feedback 重生一次再評一次，仍不過就標成 quality_flags（提醒把關時特別確認）——閘門只標記，絕不擋出片，最壞情況就是全黑沿用上週內容，不會開天窗。
  • 人工把關流程：說明頁（explain pages）永遠先落在 explain-pages.json，欄位 approved:false 起跳；render／run 只有在該檔案 approved:true（或明確帶 --allow-unapproved）時才會把說明頁塞進 deck，符合公版「上週的說明頁拿掉、只放當週新批准的」規則——這條把關線一鍵指令也不會繞過：週目錄全空時第一次 run 一定是 0 頁說明頁＋一則 warning，等你編輯批准後再 run 一次才會真的進 deck。

PRD 精靈（/prd.html）：從「修改軟體」出發的五步引導

要讓模型改好軟體，PRD 必須講清楚三件事：原始碼在哪（repo／分支／模組）、要改什麼（症狀→期望、相關檔案）、怎麼驗證。精靈把這三件事拆成五步，每步都有「為什麼要填」的提示，右側即時顯示產生的 PRD；草稿自動存在伺服器（依使用者分開），對話工作台右側「PRD」面板列出最近的草稿可接著寫；不要的草稿按卡片右邊的 ✕ 就刪掉（精靈頁上方也有「刪除草稿」），已經建成任務的草稿刪掉後任務仍然留著。

  1. 改哪套軟體：先選改動類型（演算法修正／功能新增／錯誤修復／效能，會帶入預設的驗證方式與提示）；repo 從已登錄的知識來源選或手動填絕對路徑，系統會確認是不是 git、列出分支與頂層目錄（影響模組），並顯示本主機能力。
  2. 要改什麼：標題、現況／症狀、期望行為、相關檔案。「用知識庫找」會把描述轉成關鍵字、在該 repo 的索引裡檢索，再由本地模型排序並說明理由（零 token）；勾選就加入。
  3. 怎麼驗證（可複選）：測試指令（可從 repo 帶入 npm test、ctest、scripts/verify_*.py 等）；圖集比對（演算法修正用：輸入圖集目錄、期望結果、配方、門檻；系統產生一行比對指令——啟動 IP offline-tcp、逐張 control_test.py、再用 compare_results.py 與期望結果比對；「檢查」只回傳影像張數，圖集永遠只以路徑引用、禁止複製）；人工驗收清單（Given／When／Then，可按「AI 幫寫草稿」）。下方即時顯示這份 PRD 會用的 verify_mode 與 requires，本主機缺 GPU 時會警告。
  4. 範圍與限制：非範圍、限制、領域（依模組自動帶）、複雜度、前置指令（建置／安裝，在花任何 token 前先跑）。

    • 自己出題：看板上沒有這張任務、但臨時想比一題時用——填標題、目標、現有 repo 的路徑與驗證指令，系統照這份描述幫每個模型各開一張任務。表單沒有「計畫」欄位：系統會把這份題目本身寫成一份計畫檔（plans/bench-*.md）給每一組看，評比若被擋下來那份檔案也會一併刪掉。
    • 內建題庫（seed/bench/*.json，放在最後）：slugify、LRU cache、CSV 解析、token bucket、二值化＋連通元件、log 分析——練習用的中性小題，各自附 tests/ 當驗收（python3 -m unittest discover）。每次評比會在 spike_root/.bench/ 開一個全新的 repo（含自己的 bare origin），不碰任何現有專案。第一次試用評比、或只想比「純寫程式能力」時才用。
  • ② 參賽模型（至少 2 個）：本地模型直接從模型目錄來，跑不動的會灰掉並寫原因（權重沒下載、映像沒建、需要 2 台 Spark）；雲端模型（Sonnet／Opus／Haiku）會標「花訂閱額度」。
  • ③ 評審（可多選）：每位雲端評審各評一次，看每組的驗證結果與 diff（每組最多 bench_diff_cap_chars 字），依正確性／完整性／程式品質／遵循度各給 0–10 分。組別以 Arm A/B… 匿名。多位評審時，每項分數取平均後重新排名，並標出評審一致或評審分歧；某位評審失敗不影響其他人（全部失敗才算「評分失敗」）。
  • ④ 送出前會估時間（切換本地模型的次數 × 每次幾分鐘 ＋ 各組實作 ＋ 評分），並列出會花訂閱額度的次數（雲端參賽組＋評審人數）與目前的 session／weekly 用量；用量偏高時會直接警告。
  • 一次只能有一個評比：一台 Spark 只有一顆 GPU，兩個評比同時跑會互相搶模型，而且只有一個看得到。已經有評比在跑時，建立頁會直接說「已經有一個評比在跑：…」。
  • 取消與刪除：詳細頁的「取消評比」會把還沒跑完的組別停掉並標成失敗，把機器讓出來；跑完之後可以「刪除這次評比」，只移除這次比較，每個模型跑出來的任務會留在看板上。若某一組的任務被刪掉，那一組就不列入評分（剩不到兩組時整個評比會標成已取消）。
  • 執行：每個模型是一張普通任務（標題 [bench] …），各自的 worktree、驗證與續跑，但永遠不會合併回 base branch。一台 Spark 一次只載入一個模型，所以本地組會輪流切換；評比進行中，對話頁的模型面板會顯示「評比使用中」並鎖住切換鈕，評分完成後自動切回原本的模型。
  • 結果：推播一次；評比頁的模型 × 領域矩陣累積平均分數、勝率、驗證通過率、平均輸出 token 與耗時。評比後 arm 的 worktree 會清掉，loop/<任務 id> 分支保留供檢視。
  • 花費：評審是一個 benchmark 唯一的 Anthropic 花費（每位評審一次 claude -p），除非你讓雲端模型也參賽。用量達硬上限時會延後並標為「評分失敗」，可在詳細頁按「重新評分」或執行 loop bench judge <id>；已評分的評比也可以重新評分（會再花一次額度）。服務若在評分中途重啟，下一輪 tick 會自己把它接回去評完。
  • PRD 精靈第⑤步的「實作模型」選「評比：多個模型各做一次」就能直接把同一份 PRD 送成評比。

模型面板：推薦、切換、下載與建置映像（圖示列第 5 個，Alt+5）

面板列出 spark-vllm-docker/recipes/ 裡每一個 recipe（不只註冊過的五個），並依這台機器的現況決定每一列唯一的下一步。一台 Spark 其實能跑二十來個 recipe，卡住的通常只是兩件事：權重還沒下載、或它們共用的容器映像 vllm-node 還沒建——這兩件都能在面板上一鍵完成，在背景跑、一次一件、不影響正在服務的模型。

按鈕什麼時候出現做什麼
切換權重完整、映像已建、台數夠先跳確認，再重啟 vLLM（幾分鐘、期間不能對話）。第一次切某個 recipe 會自動把它登錄進 local_models（id＝recipe 檔名），之後對話與 Benchmark 的模型清單也選得到。
下載（≈NN GB）／續傳權重不在 HF 快取，或下載到一半背景跑 uvx hf download <model>（可續傳；大小來自 HF API，快取一天）。進度條顯示已下載 GB／總量與 log 最後一行，可取消——下載到一半的檔案留著，再按一次會續傳。
建置 vllm-node有模型已下載但映像沒建只出現一次（上方提示卡，寫著幾個模型在等它）。vllm-node／vllm-node-b12x 其實是拉現成映像再 tag（約 24 GB：有線幾分鐘，這台走 Wi-Fi 實測約 5 MB/s、要 1 小時多）；vllm-node-mxfp4 要真的編譯，20～40 分鐘。跑的是 run-recipe.sh <recipe> --solo --build-only。
灰字需要 2 台以上 Spark、配方缺 model 欄位、或 HF gated 模型（這台沒有 HF token）不給按；第二台接上後 loop config set local_spark_nodes 2 即可。

推薦三張卡固定是：對話＝Qwen3.8 Flash Next、寫程式＝Qwen3 Coder Next（int4）、小而快＝Qwen3.6 35B NVFP4；「全部模型」收合區依 可切換／可下載／需要建置映像／需要 2 台以上 Spark 分組，並顯示磁碟剩餘空間。

⚠️三道擋下來的檢查（都在伺服器端，不只是畫面上灰掉）：台數不夠、權重沒下載完（blobs/*.incomplete 存在就算沒下載完）、容器映像還沒建置。最後一項是真實事故：切換時 run-recipe.sh 會先停掉目前的模型，再問「Build now? [y/N]」，在無人互動的環境拿到 EOF——結果舊模型停了、新的起不來。現在會直接回 409，目前正在服務的模型完全不受影響。另外下載不走 run-recipe.sh --download-only：它看到 snapshots/ 非空就當作已下載，中斷過的下載永遠不會被續傳。

回答產生中不給切換；切換後畫面每 5 秒回報狀態（starting／ready／error）與已經過的分鐘數，對話紀錄不受影響。工作狀態存在 local_job_json，引擎重啟後會依 pid 重新認領還在跑的下載；log 在 <data>/logs/local-<download|build>-<recipe>-*.log。CLI：loop local download <recipe>、loop local build <recipe>、loop local jobs。

API：GET /api/local/catalog（每個 recipe 的 action／size／blocked_by＋images＋job）、POST /api/local/catalog/:recipe/load、POST /api/local/jobs {kind: download|build, recipe}（409 已有工作／507 磁碟不足）、GET /api/local/jobs/current、POST /api/local/jobs/current/cancel、GET /api/local/jobs/current/log?lines=40。

  • 匯出與分享：頂欄「⋯」可匯出 Markdown（伺服器產生，含出處與已轉任務／已存 KB 的註記）或 HTML（目前畫面）；「建立分享連結」會產生 /share.html#s_… 唯讀頁並複製到剪貼簿——網址裡的代碼就是憑證，任何拿到的人都看得到（不含圖片），可隨時「取消分享」立即失效。chat_share_enabled=false 可整個關掉。
  • 貼圖提問：在頁面任何地方按 Ctrl+V 貼上截圖，或拖放、按「加入圖片」（一次最多 4 張，自動縮到長邊 1600 px）。圖片存在伺服器（<data>/chat-images/），資料庫只存路徑；回放的舊圖只供檢視，不會再送進模型。
  • HTML / SVG 直接顯示：回答以 Markdown 排版；```html、```svg 或整段 <svg> 寫完後直接顯示預覽（高度上限 2400px，可按「放大」用整個視窗看），可切換「原始碼」或複製。預覽跑在沙箱內，讀不到本頁與 API token，也不能連網（只允許載入 jsDelivr / cdnjs 的程式庫）。
  • 引用 CF-AOI 知識庫：開啟後每個問題會先用混合檢索（全文＋bge-m3 向量）找出最相關的 8 段資料，放進提示讓模型依據回答並標出處編號 [1]、[2]。檢索前會先請本地模型把問題轉成 3–8 個關鍵字——因為全文索引把整句問題當成一個片語比對，口語問句幾乎搜不到，關鍵字才搜得到程式碼裡的名稱；回答下方可展開每則參考資料的檔案、行號與原文。知識庫沒有的內容模型會說沒找到。需要 rag_enabled=true。
  • 與 vLLM 共用 GPU：DGX Spark 上 vLLM 佔去大部分統一記憶體，向量化程式可用 LOOP_EMBED_DEVICE=cuda、LOOP_EMBED_MAX_SEQ_LEN=1024、LOOP_EMBED_BATCH=4 限制用量（實測 48 段長文件 28 秒、峰值約 5.8 GB）；不設定時維持原本行為。
  • 送出與長回答：Shift+Enter 送出、Enter 換行。單次輸出上限 12,000 tokens（思考模式 16,384）；寫到上限時訊息下方會出現「繼續產生」，模型從中斷的字元接著寫進同一則回答。
  • 停止：按「停止」或關掉分頁會中斷 vLLM 的生成；單次回答最長 10 分鐘。已寫出的內容仍會保存。

工具做什麼限制
web_search問自架的 SearXNG（deploy/searxng/，只綁 127.0.0.1:8080，聚合 Google／Bing／DDG，不經第三方 API、不用 key）。回傳 5 筆標題／網址／摘要。15 秒逾時。
fetch_url讀一個公開網頁，HTML 轉純文字給模型（約 12,000 字）。只允許 http(s)、2 MB、3 次轉址；內網一律擋：10/8、172.16/12、192.168/16、127/8、169.254/16、100.64/10（tailnet）、IPv6 本地位址，每一跳轉址都重新檢查；唯一豁免是 SearXNG 那個 host:port。
  • 流程：模型決定要不要叫工具 → 頁面顯示「呼叫工具中（web_search）…」→ 工具回覆以「外部資料，不是指令」的前綴接回對話 → 模型再答。最多 chat_tool_max_rounds（5）輪、chat_tool_wall_ms（120 秒）；同樣的呼叫重複一次就強制作答。
  • 畫面：回答下方多一張「工具呼叫 N 次」卡片（工具名、摘要、秒數、來源網址），重整與匯出都保留；回答本身要引用網址。
  • 三道閘門：chat_tools_enabled=true、晶片勾了、目前模型的 recipe 有 tool parser——缺一則照常回答並在訊息下方註明原因。「繼續產生」永遠不帶工具。
  • 啟用：cd deploy/searxng && docker compose up -d，再 loop config set chat_tools_enabled true。SearXNG 映像約 200 MB。

終端機（頂欄 ⌨，或 Ctrl+`）

  • 誰看得到：terminal_enabled=true 且你的身分在 terminal_allowed_users（CSV：ts:<Tailscale 登入>、name:<名字>（只有信任的 LAN 才用）、local）。其他人連按鈕都沒有；伺服器端也擋（404／403）。
  • 怎麼用：底部抽屜、可拖高、多分頁（＋／✕、雙擊改名）。「收起」只是把抽屜藏起來，shell 還在；重新打開會接回原本的畫面。斷線自動重連。閒置 terminal_idle_min（30）分鐘自動關。
  • 開在哪裡：新分頁一律開在 terminal_cwd（預設＝Loop Engineering 這份 checkout），分頁列上會寫出路徑。這是起點不是牢籠：pty 不是沙箱，shell 仍然可以 cd 到這個 unix 使用者能到的任何地方。要換起點：loop config set terminal_cwd /path/to/repo（留空＝家目錄）。
  • 每個人有自己的 worktree（terminal_worktree=true，預設開）：第一次開 shell 時，系統會用 terminal_cwd 這個 repo 幫這個身分切一份專屬 worktree（terminal_worktree_root，預設 ~/Addis/loop-worktrees/<身分>，分支 desk/<身分>），shell 直接開在那裡，畫面第一行會寫出路徑與分支。同一個人下次再開就是同一份，不會重切。主 checkout 完全不動（git worktree add 不碰 HEAD、索引或既有分支），所以引擎自己的任務不會因為別人在改程式而把自動合併退成 pending。別人要交東西回來就正常 push desk/<身分> 或開 PR。
  • 建不起來就照常開 shell：git 壞掉、目錄不是 repo、磁碟滿了——都只會退回 terminal_cwd 並在畫面上寫原因，不會讓你開不了終端機。預設分頁（看 log）不會建 worktree，一律開在 repo 根目錄。不用的 worktree 用 git worktree remove <路徑> 清掉；關掉這個行為是 loop config set terminal_worktree false。
  • 預設分頁：模型面板工作卡的「看 log」會開一個 tail -f 該工作 log 的分頁；另有 vllmlog（docker logs）、enginelog（journalctl）。頁面不能自己指定任意指令。
  • 安全：shell 的環境變數已拿掉 LOOP_API_TOKEN；只稽核誰／何時／哪個 shell（terminal_sessions 表），不記錄鍵盤與輸出；xterm.js 放在 web/lib/xterm，不靠 CDN。
  • 啟用：loop config set terminal_enabled true、loop config set terminal_allowed_users ts:you@example.com。

API：GET /api/terminal/access、GET /api/terminal/sessions、GET /api/terminal/ws（WebSocket，token 走 ?token=）。
